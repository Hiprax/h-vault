# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **A vault-key rotation stopped by a crash or a lost connection can now be finished.** Rotating your vault key re-encrypts everything under a new key, and until now an interruption part way through left the account in a state nothing could resolve: any entry already re-encrypted was sealed under the new key, the rest were still under the old one, and the new key itself was thrown away the next time you signed in — so those entries were unreadable for good, by anyone. The key is now kept, your Settings page says an interrupted rotation is outstanding, and the **Finish Rotation** button completes it using that same key rather than generating yet another one, reading each entry with whichever of the two keys opens it. Until it is finished the server refuses to rotate to any other key, because it cannot see which entries the interrupted rotation had already moved and rotating past them would make them unreadable for ever behind an apparent success. Abandoning the interrupted rotation is still possible — it has to be, because its key is sealed under the master password that was in force at the time, so changing your password makes finishing impossible — but it is a separate action that says plainly what it costs.

- **Two settings now control how long the server will wait to receive a request** — `HTTP_REQUEST_TIMEOUT_MS` (four minutes by default) and `HTTP_HEADERS_TIMEOUT_MS` (one minute). They bound how long a request may take to ARRIVE, never how long it may take to process, so a key rotation or a backup restore that legitimately runs for minutes is unaffected. The default is the largest body any endpoint accepts — a 30 MB backup restore — at the slowest upload speed this deployment stands behind; raise it if your users upload large backups over slower connections than that. Until now neither was set at all, and the server inherited a five-minute wait from the runtime.

- **A setting for how long the server waits for one upload piece, `DOCUMENT_PART_BODY_TIMEOUT_MS`.** It defaults to sixty-four seconds, one 8 MiB piece at the slowest connection speed the app is built for, and may be raised up to the limit on receiving any request (`HTTP_REQUEST_TIMEOUT_MS`, four minutes by default). Raise it when users upload several files at once over slow links, since those transfers share one connection; raising it also lengthens how long an account can hold an upload slot while sending nothing.

### Changed

- **When a file cannot be repaired or formatted before upload, the explanation is now the app's own.** It still names the line and the column and quotes the line itself, and for the JSON repairer it still says what was wrong ("The repairer expected a colon."), but the formatter's own error text is no longer shown: it was written by the tool rather than by the app, and there is no way to show some of that text without showing whatever a compromised tool chose to put there. A tool that fails without saying where is now described as the tool having stopped, rather than as a mistake in your file.

- **The notice that appears when your vault key was changed elsewhere now offers to sign you out, not to reload.** Reloading could never clear that condition: the browser keeps its own copy of the replaced key, so a reload asked for your master password and then handed you the same superseded key, with the same notice straight back in front of it. Signing in again is the only thing that reads the current key and, with it, the entries the other device re-encrypted.

- **Restoring a backup this app cannot authenticate now asks you first.** Every backup you download carries a signature, and restore has always checked it when it was there — but a file with that signature simply deleted used to restore anyway, behind a notice there was nothing to do about. It now stops and asks, naming why it could not be verified, and sends nothing until you answer. Three ordinary cases land here as well as a tampered one: a backup that arrived by email, which carries no signature at all because the server that assembles it has no backup password to sign with; a backup written before signing existed; and a backup from another account or from before you changed your backup password, whose signature can only ever be checked against the copy of the key carried inside the file itself. A file whose signature no available key agrees with is still refused outright, and the refusal no longer tells you the file was tampered with, because a file signed under a different backup password fails in exactly the same way and nothing in the browser can tell the two apart.

- **A file upload can now be told to wait a moment when your own account already has several parts in flight.** Uploads are sent in 8 MB pieces, and the server buffers only a few at a time across everyone using it. One account may now hold at most three of those at once — which is exactly as many as it can have transfers open, so an upload started from the app is never refused — and anything beyond that is answered with "try again in a second" rather than being queued behind work nobody is doing. The app retries on its own and the transfer continues; nothing is lost, and nothing is stored twice.

- **An upload piece that has not fully arrived within sixty-four seconds (by default) is now dropped, rather than after five minutes.** That is one piece at a deliberately slow connection speed, with the rest of the application still allowed the full four minutes for its much larger backup and rotation requests. Operators whose users upload over slow links can raise it with the new `DOCUMENT_PART_BODY_TIMEOUT_MS` setting. The transfer stays resumable, and the app retries it by itself.

- **A second backup restore or vault-key rotation started while one is already running on your account is now turned away straight away.** Both operations already refused to run side by side, but the second one was only told so after the server had received and read its whole upload, which can be up to 30 MB. It is now answered at once, with the same kind of refusal and a message asking you to wait for the one already running, before any of that upload is read. Two different accounts are unaffected, and when several accounts restore or rotate at the same moment the server now takes a couple at a time and has the rest wait their turn rather than reading all of them into memory together.

- **Two-factor secrets stored from now on no longer stall the server each time they are read.** The server keeps every account's authenticator secret encrypted under its own configuration key, and it derived that encryption key with 600,000 rounds of PBKDF2, a work factor meant for passwords people choose, on the same thread that answers every other request: about a third of a second per setup, per sign-in code and per wrong code. The key is a long configuration secret rather than a password, so secrets stored from now on use 10,000 rounds, about 5 ms. Secrets stored earlier keep working exactly as before, at their original cost, until the account next sets up two-factor sign-in, and confirming a new setup no longer encrypts the same secret a second time.

- **The file encryption tool now says why it cannot open a file sealed with unusually heavy key-derivation settings, instead of "Something went wrong. Please try again."** An `.enc` file made elsewhere with settings above what this browser will run is refused before any work starts, with a message that says so and that files encrypted with H-Vault are not affected; retrying could never have succeeded. A file too large for the container format now shows the same "too large" message the size limit does.

- **The format-and-repair step for uploads now uses Prettier 3.9.8 (was 3.9.6).** A document formatted from now on records `prettier 3.9.8` as the tool that formatted it. JSON and YAML come out exactly as before; Markdown differs only in corner cases where the 3.9 releases had regressed (some since 3.9.0) and the new release restores the earlier output: a single-tilde subscript such as `H~2~O` is kept rather than rewritten as strikethrough, and block quotes, headings inside block quotes, task lists, indented code inside list items and Liquid tags are formatted as they were before. Documents already stored are not touched.

- **The server now reads `.env` with dotenv 18 (was 17), and the environment still wins over the file.** The file is parsed exactly as before: quoting, comments, `export`, values spanning lines and `\n` inside double quotes are unchanged. dotenv 18 also takes its own options from `DOTENV_*` and `DOTENV_CONFIG_*` environment variables, so the server now pins how the file is read, and such a variable still cannot make `.env` replace a setting the environment already holds, have the file read in another encoding, or point the server at another file. The start-up line that reports how many settings were loaded from `.env` is now written to standard error instead of standard output, without the rotating tip.

### Removed

- **Encrypted `.env.vault` files are no longer read.** H-Vault never documented them; the server's `.env` loader, dotenv 18, dropped them, together with the `DOTENV_KEY` variable that unlocked them. A plain `.env` is read exactly as before.

### Fixed

- **Starting an upload at the moment another one finishes can no longer take an account past its storage quota.** A new upload is checked against two totals, the files already stored and the uploads still in progress, and the two were read at the same time. An upload finishing in between moved out of the second total before it appeared in the first, so neither counted it and the new upload was admitted as if that space were free. The totals are now read in an order where a finishing upload can only be counted twice, which at worst asks you to try again. On a deployment whose database connection prefers reading from replicas, these totals and the two upload limits are now always read from the primary, which has seen the previous upload's entry.

- **An authenticator export is no longer refused when its batch number is negative.** Google Authenticator numbers its exports with a random signed 32-bit value, which can be negative, and a negative one arrives in the ten-byte form the format uses for negative numbers. The importer read it as an unsigned number far too large to hold and refused the whole export as unreadable, so an export could fail for no reason the user could see or fix. The batch number is now read as the signed value it is.

- **Reordering folders no longer leaves the folder list showing an order the server does not have.** A reorder is one request per folder that moves, and when one of them was refused part way through (a lost connection, or the per-account limit on folder changes) the list kept showing the new order while the server had applied only some of it. The folder list is now read back from the server after every reorder, once every request has finished, whether it succeeded or not.

- **Signing in, locking and signing out will not hang when a future update upgrades the browser's offline storage while H-Vault is open in another tab on a different version.** The encrypted offline copy of your vault and your saved Vault Health results each live in a browser database that a future update will need to upgrade, and an upgrade has to wait for every other tab holding that database to let go. No release so far has needed that, so nothing could hang yet; this is the groundwork that stops the first such upgrade from leaving a sign-in, a lock or a sign-out (one that had yet to finish clearing the session) waiting for ever on a tab that never lets go, with nothing on screen. Each tab now steps aside as soon as another tab needs to upgrade; a wait of more than a second is given up rather than left open, and the app then says what happened: offline access is unavailable because H-Vault is open elsewhere on a different version, and it names the remedy (reload or close the other tabs, then reload this one). The same message replaces _"offline storage is not working in this browser"_ for a tab whose database a newer version has already upgraded. A request the browser never answers at all, which is what a tab waiting behind another tab's upgrade gets, is given up after fifteen seconds and reported as offline storage not working, since the tab cannot tell which it is. Signing out now also forgets which account the offline copy belonged to when clearing that copy fails.
- **Saved Vault Health results are no longer wiped by a save that could not read them.** Saving a breach-scan or password-strength result reads what is stored, merges the new result in and writes the whole set back. When the read itself failed, the save carried on as if nothing had been stored and replaced everything, so earlier breach findings or strength scores disappeared. A save whose read fails now writes nothing, and what was stored is kept until a later save can read it.
- **A vault-key rotation interrupted by a crash is no longer quietly destroyed by changing your master password.** Such a rotation leaves a second key on your account — the one it was moving to — and every entry it had already re-encrypted can be read only with that key, which is why your Settings page offers to finish it. Changing your master password re-seals the key your vault is using and, until now, left the other one sealed under a password that no longer exists: **Finish Rotation** could never open it again and those entries were gone, at the moment the password changed, with nothing said at the time. The change now moves both keys together, and is refused rather than allowed to strand one — if it is refused, reload the page and try again. A password _reset_, which mints a brand-new vault key and cannot carry anything across, now clears the outstanding rotation instead of leaving an offer that can never succeed and blocking every later rotation.
- **A rotation that fails now updates what the page offers next.** A rotation that got far enough to record its new key is refused if you then try to rotate to a different one — correctly, because that would strand whatever it had already re-encrypted — but the page went on showing **Rotate Key**, so each retry re-encrypted the whole vault and met the same refusal. Only reloading broke the loop, and nothing said to. The refusal also said what to do about it in a sentence too long to be shown, so the part that mattered was cut off mid-word; it is now short enough to read.
- **A request body nested absurdly deep is now refused as malformed instead of failing as a server error.** A body only a few kilobytes long, built from ten thousand levels of nesting, exhausted the server while it was being screened and came back as a 500. Anything nested more than 32 levels is now refused with a 400 before it is read further; no request the app sends comes close to that.
- **Reading a photo of an authenticator export can no longer leave the tool stuck.** A reply the scanner could not make sense of ended the session without telling the attempt that was waiting on it, so the Upload a photo button stayed disabled for as long as the page was open. It is now always told, and says why.
- **A browser that cannot read images at all now says so instead of scanning in silence.** That refusal was being reported as a problem with the individual photo, so the camera went on taking frames and rejecting every one of them with nothing on screen. It now stops and explains.

- **A locked account can no longer be held locked for ever by anyone who knows the address.** Ten wrong passwords lock an account for thirty minutes and email its owner a link that ends the lockout sooner. The link was tied to the exact moment the lockout was due to end, and the counter behind the lockout is only cleared when somebody actually completes a sign-in — so an account that was locked and then left alone sat permanently at the threshold, and every further wrong password pushed the deadline out by another thirty minutes and, in doing so, killed the one link its owner had ever been sent. No replacement was sent either, because the email only went out on the attempt that first crossed the threshold. One wrong password every half hour, from anyone who knew the address, was enough to keep somebody out of their vault indefinitely; and since resetting the master password here generates a new vault key, the only way out destroyed everything in the account. The link is now tied to the lockout itself rather than to its deadline, so it keeps working however many times the lockout is extended, and a fresh one is sent only when the outstanding link would expire before the lockout it covers. That is at most one new email per link lifetime — about one every half hour while an attacker keeps the lockout alive, rather than one in total — so a grinding attack still cannot be turned into a flood of them; when a replacement does go out the link it replaces keeps working until its own hour is up, and either of them ends the lockout.

- **A thirty-minute lockout no longer destroys a thirty-day session.** An account is locked for half an hour after ten wrong passwords, and a lockout can be imposed by anyone who knows the address. While one stood, every signed-in session on every device was silently destroyed as it went to renew itself: the renewal spent the session's token and issued its replacement before it checked the account, so the refusal was answered after the old token had already been consumed and the new one existed only inside a reply that was never sent. Both halves were gone, permanently, and the browser was told to discard the cookie as well — so the natural next move, trying again with the cookie still held, looked like a stolen token being replayed and revoked every remaining session and every device trusted to skip two-factor. "Remember me" made it worse rather than better, because what was lost was a thirty-day session rather than a seven-day one. The account is now checked first: a renewal during a lockout is refused without spending anything, the cookie is left exactly as it was, and the same session resumes the moment the lockout is discharged by its deadline or by the emailed unlock link. The app says the account is temporarily locked and offers to try again, instead of signing you out, and it now says so in words wherever a lockout surfaces — including the sign-in screen, which used to show the bare code; renewals refused for any other reason — an unknown, expired or replayed token, or an account being erased — still end the session exactly as before, and replaying a token still revokes the whole family whether the account is locked or not.

- **One unreadable entry no longer blocks the whole vault-key rotation, for ever.** A single item, folder or document whose stored data would not decrypt used to stop the rotation before it began, with nothing sent to the server — and since the next attempt met the same entry, the account could never rotate its key again. Such an entry is already unreadable with the key the vault holds, so the rotation now carries it across exactly as it is, re-encrypts everything else, and tells you afterwards how many entries were left behind and of what kind. The one case that still stops everything is the one where nothing at all could be read, which means no key that rotation is holding opens the vault rather than that the data is damaged; it says so plainly, changes nothing, and now names the remedy that actually fits. If you were rotating, or finishing an interrupted rotation, the remedy is to sign in again, since the likeliest cause is a session still holding a key the account has replaced. If you were _abandoning_ an interrupted rotation, it is to finish that rotation instead — nothing was abandoned, so it is still on offer, and your entries are most likely sealed under the key it was moving to — a case where signing in again, or reloading, cannot help. A vault holding a single entry is also told so in words, rather than as "none of the 1 entries".
- **The API reference now lists the conflict response that six write endpoints could already return.** Creating or updating a vault item or a folder, importing and restoring a backup are all refused while a vault-key rotation is being processed, and have been for as long as the rotation fence has existed — but the published API document never said so, so anyone writing against it had no reason to handle it. Each of those six operations now documents that refusal, alongside the duplicate-folder-name and concurrent-import conflicts that share the same status.
- **The API reference now quotes the real rate limit for changing your master password.** It said three requests per address per fifteen minutes; the limit is five per account per fifteen minutes, counted against your account rather than your network, so that sharing an address with somebody else has never spent your budget. The description also now says what the endpoint does to your other sessions, which it has always done and never stated: every signed-in session and every device trusted to skip two-factor is revoked.

- **The API reference now lists the "too many requests" response on sixteen more endpoints that could already return it.** Refreshing a session, signing out, reading your profile, folders, sessions, trusted devices, audit log and backup history, changing settings and backup settings, the single password breach check and the health check are all rate limited, and none of them said so. Six endpoints that were missing from the reference altogether are now documented as well: recording a vault lock, verifying an unlock, regenerating two-factor backup codes, deleting the account, the public configuration and the operator metrics. A check now fails the build if any rate-limited endpoint is left out of the reference or omits that response. The request for turning off two-factor authentication also lists the password it has always required.

- **Reading your authenticator codes from a photo now works at all.** The import tool offers three ways in — the camera, a photo of the code, and a pasted export link — and the middle one had never once succeeded, for two separate reasons. The photo was handed to the isolated document that reads it in a way that is only valid for a live camera frame, and the browser refused it before it was ever sent; and even without that, the photo was offered to that document in the same instant it was created, before it could possibly be ready to take anything, and was turned away. The camera never showed either fault, because it simply tries again with the next frame an eighth of a second later, while a photo gets one attempt — so every photograph, however good, ended at "That image could not be read.". Each failed attempt also left one more hidden, invisible frame attached to the page for as long as it stayed open. A photo is now held until the document is ready and then read, and the frame it needs is taken down whether the read succeeds or fails. This matters most on the machines the feature exists for: a laptop camera is often too coarse to read a dense export, and photographing the codes with a second phone was the documented way around that.

- **A photo the scanner cannot read no longer stops the scanner.** Some images are refused unread: too many bytes, too many pixels, or a format the browser cannot decode at all. A 48-megapixel photograph and a picture straight off an iPhone are both ordinary examples. The refusal could not be attributed to the photo that caused it, so it ended the whole scanning session — and if the camera happened to be running, it stopped that too, mid-aim, with nothing on screen to explain it. Each of those refusals now names the image it belongs to, so only that image is refused, and what you are told is the specific reason rather than "That image could not be read." An oversized file is also turned away before it is handed over at all, which is faster and says what the limit is. Only two things still end a session, and neither can be improved by trying another photo: a request the reader could not make sense of, and a reader that would not load.

- **A slow scan no longer stops the camera.** Each image gets four seconds to be read before the scanner gives up on it and takes the next frame, which is the right answer while aiming at a moving phone. An answer that arrived just after that deadline was treated as a reply to something never asked for — the rule that protects the session from a frame gone wrong — and it shut the whole scan down, camera and all, with nothing on screen to explain why. A late answer to a question the scanner has already abandoned is now simply dropped, and scanning continues. A reply that matches nothing the scanner ever sent, or a second reply to one it did, still ends the session exactly as before.

- **The coverage gate no longer refuses a push over a line nothing changed, nor waves through one that nobody tested.** The gate asks whether the production lines a change touched are covered, and it worked out which lines those were by combining three separate comparisons: against the last commit, against what is staged, and against what is merely saved. Those three number a file's lines differently the moment anything is uncommitted — the normal state while work is in progress — and the combined answer was then looked up in coverage measured from the files actually on disk. It could therefore refuse a push over a comment, and, the half that mattered more, pass silently over a genuinely untested new line whenever that line's number in the last commit happened to land on a tested line on disk. The gate now builds one comparison, against the files on disk, and measures exactly that; files that have never been committed are folded into the same comparison rather than counted separately.

- **An upload abandoned at the wrong instant no longer costs the server a slot for the rest of the day.** Closing the tab, losing the network or cancelling an upload in the fraction of a second while the request was being checked left the server holding a piece of its upload budget that nothing would ever hand back. Repeat that a few times — over hours or over a bad connection — and every file upload on the server, for every account, waited for ever with nothing logged and no error anywhere. The budget is now returned in that case too.

- **An upload the server gave up waiting for is now retried instead of being marked failed.** A stalled connection, a laptop that slept mid-transfer, a phone that changed network: when a request as a whole takes too long to arrive the server answers "you took too long", which the app treated as a permanent refusal (the same as a corrupt piece or a bad request) and stopped the transfer. A single upload piece that misses its own, shorter deadline has its connection dropped instead. Both are now treated as the interruption they are, the same way the app already treats a connection that simply drops: three retries, a second apart at first, and the transfer resumes where it left off.

- **The API reference now states the rate limits the server actually applies.** Seventeen endpoint descriptions carried figures from an earlier configuration (for example "3 requests per IP" where the real budget is 5 per account, or 20 per IP); each now names its real limit and what it is counted by.

- **Cancelling a small upload now frees its storage straight away.** A file small enough to go up in one piece is written to storage as soon as it arrives, and cancelling it (or signing out, which cancels every upload in progress) only forgot the upload: the file itself stayed in the bucket for at least a day, until the hourly clean-up found it, while the upload slot and the space it had reserved were handed back at once. So those bytes sat on the operator's disk counted against no one, and anyone repeatedly starting and cancelling small uploads could hold storage that no quota saw. The stored file is now deleted as part of the cancel. A cancel that arrives in the same instant the upload is being finished is decided one way or the other: either the upload is cancelled and no document appears, or the document is kept intact and the cancel is told the upload no longer exists. A cancel that lands while the file is still being written is covered too: the write that finishes after it deletes what it stored, unless a document already owns it.

- **Finishing several uploads at once can no longer carry an account past its storage quota.** Each finished upload is checked against the quota using the files already stored, and two uploads finishing together could each see room for themselves before either was recorded, so both were kept and the account ended up over its limit. Finished uploads for one account are now checked one at a time, each against everything stored before it. One that arrives while another is being checked is asked to retry and keeps every byte it uploaded; if the retry then finds no room, it is refused with the usual quota message and its file is removed, exactly as a single over-quota upload already was.

### Security

- **An upload piece whose sender disconnects no longer frees its upload slot before the server is done with it.** The server stores each piece before answering, and a piece whose connection dropped while it was being stored stayed in memory until that finished, yet its slot was handed back the moment the connection closed. So one account could send a piece, disconnect, and send the next, keeping more pieces in memory than its share of the slots allows. The slot, and the account's share, now come back only once the server has finished with the piece, exactly as the backup-restore and key-rotation requests already worked.

- **The isolated document viewer can no longer put its own words in the app's interface.** Previews, the format-and-repair step for uploads, and reading authenticator codes from a photo all run inside a locked-down frame that holds no key and can reach nothing, precisely so that a flaw in one of the third-party parsers it runs cannot touch your vault. But when that frame declined something it sent back its own sentence, and the app showed it as its own: beside the real Download button, in the upload panel, and in the import tool's status line. A compromised parser could therefore have written up to a paragraph of anything there in the app's voice — "re-enter your master password at …" — which is exactly what drawing that part of the screen outside the frame is meant to prevent. The frame now reports only which of a fixed set of refusals it is, and every sentence you see is the app's own; anything else it sends is discarded, and a refusal the app does not recognise is described in general terms and never repeated. The labels naming the tools that reformatted an upload, which are shown before you confirm it and stored with the document, are now decided by the app from what it asked for, and a result labelled any other way is refused. Two pieces of text still come from inside. One is the line of your own file that a failed repair or format points at, and the app now quotes even that from its own copy of the file whenever it has the text the line refers to. The other is the address of a link in a document you are viewing, shown in the dialog that asks before opening it; see the next entry.

- **A link in a document you are viewing can no longer put words of its own in the dialog that asks before opening it.** That dialog shows where the link goes, and the address came straight from the isolated viewer, which a crafted file could make send any text at all: a `mailto:` followed by a sentence, or a string that is not an address, shown in bold where the destination belongs. The address is now read as a URL first. What the dialog shows is the address as the browser itself would write it (spaces, invisible characters and text-reversing controls encoded, a lookalike domain in its plain `xn--` form), the destination line is taken from that parsed address, a long address is cut short, and anything that is not an http, https or single plain mail address is not offered at all.

- **A crafted authenticator export can no longer read as different accounts to different programs.** Importing from Google Authenticator reads the export's fields by number, and each field number arrives packed into a value the format caps at 32 bits. A crafted export could carry a wider value there; this app kept only the low 32 bits of it, so a field number the format does not allow at all was read as an ordinary account entry, while some other readers of the same export refuse it outright, so which key you were offered depended on which program read the code. Such an export is now refused as unreadable, as is one using field number 0, which the format reserves and no genuine export contains; one carrying a number wider than 64 bits, which made a counter-based account's counter a value different readers disagree about; and one spelling a field number, a length or a small number in more than five bytes, which no encoder writes and which some readers skip past while others refuse it, so that the rest of the export reads differently to each. Exports from Google Authenticator itself are unaffected.

- **The ten-per-quarter-hour budget for heavy operations is now counted per account rather than per network address.** Emptying the trash, bulk delete and bulk move, export, and triggering or downloading a backup share that budget, and everyone behind one office or household connection used to share it too, so one person's export could refuse another's. An attacker holding one account could also buy a fresh budget by changing address; that no longer helps. The warning the server logs when this budget runs out now reads `heavyOpLimiter rate limit exceeded`.

- **Confirming a new two-factor setup now has its own per-account budget of twenty attempts per quarter hour.** It used to draw on the address-wide budget the email-verification, password-reset and account-unlock links share, so the same neighbours could exhaust it, and a stolen session could keep guessing from new addresses.

- **Creating, editing, trashing, restoring and deleting vault items and folders is now rate limited.** Each of those writes an entry to your audit log, which is kept for a year, and none of them had a limit, so a signed-in session, or a stolen one, could fill the log without bound. Items and folders each get a per-account budget sized for the app's own bulk actions, which send one request per item: two passes over the most items an account may hold (20,000 per quarter hour) and two full re-sorts of every folder (1,000). A bulk tag or trash purge over a whole vault still completes, and spending either budget never blocks signing out or loading your folders. The budgets bound how fast one account can add to its log, about two million entries a day at the ceilings, rather than how large the log can get.

- **A locked account is now guaranteed its unlock email even on a database that serves reads from a replica.** The link is created and then read back to be addressed; on a deployment whose connection string prefers a secondary, that read could legitimately arrive before the write and no link was sent at all — the exact silence the link exists to end. The read is now pinned to the primary.

- **A backup's signature is now checked against your account's own key, not against a key the file supplied.** Restoring a backup needs a backup wrapping key, and one arrives in two places: stored on your account, and copied inside the backup file. Restore used to prefer the copy inside the file — so anyone who handed you a backup along with "its" backup password supplied both the file and the key that authenticates it, and the signature that verified proved only that the file agreed with itself. Your account's own key is now the first the signature is offered to, and the copy inside the file is consulted only after your own key has disagreed — which is what a cross-account restore still needs, since that file's signature was never made with your key. A signature that verifies under your own key restores as before; one that could only be checked against the file's own copy now says so and asks before restoring.

- **Four ways of spelling one address no longer hand out the document viewer stripped of the isolation it depends on.** Every stored file is displayed inside a separate, deliberately powerless document: it holds no key, no token and no cookie, and the rules that keep it that way are attached to it as it is served — it may open no connection of any kind, run no worker, and it sandboxes itself even if something forgets to. Those rules are what stands between a malicious file and the page holding your unlocked vault. They were attached by the address that served the document, and the address was matched exactly as typed, while the file lookup underneath it first tidied the address up. So four spellings of the same URL — a dot written as `%2E`, a doubled leading slash, a trailing letter or a leading letter written as its code — missed the rules entirely and were answered with the same document straight off disk, carrying the main application's far more permissive rules instead. Nothing looked wrong: the viewer worked, and a file opened that way would have run with the ability to reach the network and to talk to the page around it. The document is now kept outside the directory the file server can reach at all, so there is no copy for any spelling to find — the same approach already used to keep it away from the web server in front. Those addresses now return the ordinary application page, exactly as any other unrecognised address does. Nothing changes for the viewer itself.

- **An account whose deletion is still being finished can no longer be signed into.** Deleting an account erases its data in one sweep, and when that sweep fails part way through the account is left marked as still needing erasure so a background job can finish it, which it does within six hours. Everything that checks an existing session refused such an account, but signing in afresh did not — so for up to six hours the correct password still produced a working session, a new device record and an audit trail, all written against an account in the middle of being erased. Signing in is now refused, with exactly the same answer a wrong password gets so that nothing new is revealed about the address, and nothing at all is written. A two-factor challenge issued in the minutes before the deletion was requested is refused at the second step for the same reason. An account whose deletion was abandoned is unaffected and signs in normally.

- **Changing your master password and rotating your vault key can no longer be made to destroy the vault by running at the same moment.** Both operations replace the single stored copy of your vault key, from opposite directions: one re-wraps the existing key under your new password, the other stores a new key wrapped under your current one. Started together they could interleave so that whichever finished second overwrote the other's work, leaving an account with a password that worked and a wrapped key nothing could open — every item, folder, note and document gone, with no recovery anywhere. The two are now held apart for their whole duration, and because a rotation reads your account before it starts, it also checks at the moment it stores the key that your master password has not changed since; if it has, it rolls back what it had re-encrypted and asks you to sign in again and retry. Whichever one loses says so plainly and can be retried. This closes the narrow window named as deliberately left open in the entry below about changing your master password from a stale tab.

- **An import, a backup restore and a document upload can no longer land entries under a key that is being replaced as they arrive.** All three check which vault key they are using, but the check was a read taken some distance from the first entry written: an import parses and validates a whole file first, a restore does the same and then counts four collections, and a document upload waits for the storage service to assemble the file, which is seconds for a large one. A rotation starting anywhere inside those gaps had already listed your vault without the arriving entries, so they were sealed under a key the account was in the middle of replacing — unreadable from the moment they landed, and silent about it. For a document the consequence went further: an unreadable document cannot be re-keyed, and a rotation refuses to run unless it covers every entry, so a single badly timed upload permanently ended that account's ability to rotate its key at all. Each of the three now holds the account's key steady from its check until its last write, and a rotation that arrives meanwhile is asked to wait. The cost is named rather than hidden: finishing several document uploads at the very same instant now completes them one at a time, and the ones asked to wait keep every byte they have already uploaded — retrying re-sends none of them.

- **Setting up or re-keying backup encryption from a stale session no longer quietly breaks restoring that backup into another account.** Both of those actions store your vault key sealed under your backup password, and that sealed copy is what a restore into a different account opens. A session still holding a vault key that had been rotated elsewhere wrote the old key there, replacing the correct copy the rotation had just stored. Nothing appeared to go wrong: your vault kept working, and restoring into the same account uses a different path that was unaffected. The failure surfaced only much later, when somebody restored one of those backups into another account and every single entry failed to decrypt. Both actions now say which vault key they sealed and are refused if it is not the one your account is on, exactly as saving an entry already is. Clearing a stale sealed copy still works, which is what the app does for you right after a rotation when you have no backup password set.

- **A vault-key rotation whose last step is interrupted no longer undoes itself over a rotation that had already succeeded.** The rotation re-encrypts every entry and then stores the new key; if the connection dropped at that final step, the server could not tell whether the key had been stored or not, and it assumed the worst and restored every entry to its previous encryption. When the key HAD been stored, that restore was the thing that destroyed the vault: the entries went back to a form only the replaced key could read. It now asks what actually landed before undoing anything, undoes nothing when it cannot tell, and still restores in full when the key genuinely was not stored.

- **Nothing but a completed rotation now destroys an interrupted one's vault key.** When a rotation was cut short, the server recorded the key it was moving to — wrapped under your master password, so only you can open it — precisely so the work could be picked up again. Two things then deleted it, along with the one route back to every entry the rotation had already re-encrypted: your next sign-in, and any later rotation that failed or was refused, including the retry the failure message asked you to make. Nothing anywhere held another copy, and the app never read that record, so the loss was silent and complete. Signing in now clears only the marker that was blocking writes, a rotation drops the stored key only when it actually commits, and your audit log and profile both say that a rotation is outstanding so the app can offer to finish it.

- **A tab left open somewhere else can no longer save entries that nothing will ever be able to read.** Rotating your vault key re-encrypts everything under a new key, but it does not sign your other sessions out or hand them that key — so a tab open on another machine went on holding the key that had just been replaced, still able to read what it had already loaded and still able to encrypt. Everything it saved from that moment on was sealed under a key the account no longer had. It looked saved, and it was stranded the instant it landed: the rotation had listed your entries before that one existed, and no later rotation could read it either, so it came back as an unreadable entry with no explanation and no way to recover the content. No unlucky timing was needed; the rotation could have been days earlier. Every write that stores encrypted content now says which key it used — creating and editing an item, creating and renaming a folder, importing, and restoring a backup — and the server refuses it unless that is the key your account is actually on. A request that cannot say which key it used is refused as well, once the account has rotated at least once, because a client that cannot name the key may be holding the replaced one; an account that has never rotated is unaffected, so nothing that worked before stops working. For an import or a restore the check is made immediately before the first entry is written rather than when the request arrives, since both spend a noticeable time being checked first and a rotation can finish inside that gap. Changes that have an endpoint of their own and store no encrypted content — moving several entries at once, trashing, restoring from the trash, reordering folders, deleting a folder — are deliberately left alone, because a rotation neither reads nor rewrites any of that. Changing one entry's folder, favourite or tags is not among them: it is sent to the same address as changing that entry's contents, and it is refused with the rest. That is on purpose — deciding whether to check from which fields a request happens to carry would put the check behind a choice the sender makes — and it costs nothing, because naming the key needs no key. When a write is refused, a notice appears saying your vault key was changed on another device and offering to sign out. It deliberately does not fetch the new key and carry on: everything already on screen was read with the old one, so adopting a key mid-session would leave the app holding two kinds of data at once. Signing in again starts from a single consistent state, which is why it is the only remedy offered and why the notice cannot be dismissed. Reloading the page is not enough and is deliberately not offered: the browser keeps its own copy of the replaced key, so a reload would ask for your master password and then hand you the same superseded key again.

- **A tab left open somewhere else can no longer destroy your vault when you change your master password.** Rotating your vault key replaces the key everything is encrypted under; changing your master password re-wraps that key under your new password and stores the result as the only copy there is. Those two facts together had a sharp edge. Rotating the key in one place does not sign your other sessions out or hand them the new key, so a tab left open anywhere — another browser, another machine, a phone — went on holding the key that had just been replaced, able to read everything it had already loaded and with no way to notice anything had changed. Changing your master password from that tab uploaded a wrapper built from the replaced key, and because a wrapper is opaque to the server there was nothing to tell it apart from a correct one. It was stored, the live key's only copy was gone, and every item, folder, note and document in the account became permanently unreadable — by you, by this app, by anyone. Nothing could have recovered it. No unlucky timing was needed: the rotation could have been days earlier. A change of master password now says which key it was built from, the server refuses it unless that is the key the account is actually on, and the refusal is checked again as part of the write itself, so a rotation finishing in the same instant is caught too. A request that cannot say which key it used is refused as well, once the account has rotated at least once, because a client that cannot name the key may be holding the old one; an account that has never rotated is unaffected, so nothing that worked before stops working. One that arrives while a rotation is still being processed is asked to wait. The refusal is not a dead end: it carries the key generation your account is on, and this app recovers from it without asking you to retype anything — it fetches the live key, re-wraps it under your new password and retries once, telling you plainly what to do if that does not settle it. The **Change Password** and **Rotate Key** buttons also now hold each other back, so the two can no longer be started at once in the same tab.

- **A two-factor sign-in that cannot be completed no longer leaves the key derived from your master password sitting in memory.** Typing your master password derives the key that unlocks your vault, and a sign-in that also needs a code from your authenticator has to hold that key while you go and fetch one; if you walk away instead, it is wiped five minutes later. Some refusals at the code step mean the attempt is over rather than correctable — the five minutes ran out, the sign-in was started on a different device, the account no longer exists, or it was locked in the meantime — and the app was meant to wipe the key the instant one of those came back. It never did: it looked for the reason in a place the server has never put it, so every refusal read as "try the code again" and the key stayed in memory for the remainder of the five minutes, on a screen that could not have accepted any code. Those refusals are now recognised, the key is wiped as soon as one arrives, and you are taken back to the sign-in form to start again rather than left at a code box that can lead nowhere. Everything correctable is deliberately unchanged — a mistyped code, a rate limit, a server error, a dropped connection — so the key stays and the five-minute wipe stays armed, and you can simply retype the code.

- **One account can no longer stall file uploads for everyone.** The server buffers a small, fixed number of upload pieces at a time, and it takes one of those slots the moment a request arrives rather than once its data does — deliberately, because that is the only order in which the limit bounds memory at all. It also meant that a few requests from a single account that announced a piece and then sent nothing could occupy every slot, with no file, no upload started and no storage used, and every other account's uploads simply waited. Two things now prevent it: no single account may hold more than three quarters of the slots, and a piece whose data has not all arrived within sixty-four seconds (by default) is dropped instead of being waited on for the five minutes the runtime allowed. Uploads from the app are unaffected — it can never present more pieces at once than the limit permits.

- **A backup restore or vault-key rotation is now rate limited before its upload is read, not after.** Both accept a body of up to 30 MB, and both checked the per-account limit of five attempts per fifteen minutes only once that whole body had been received and parsed, so the sixth attempt cost the server exactly what the first five did before it was refused. The limit now runs first, and the number of these large requests the server holds in memory at once is capped, counted until the operation has finished rather than until the connection closes, so dropping the connection part way through does not free the space while the work continues.

- **A backup restore and a vault-key rotation are now screened for database-operator and prototype-pollution keys, like every other request.** The server strips any key that begins with `$`, and any `__proto__`, `constructor` or `prototype` key, from a request body before anything reads it. These two requests are read by their own larger parser, which runs after that screening, so their bodies reached the server unscreened, and only the strictness of their validation stopped such a key from going further. Both are now screened straight after they are read, and a check over the whole route table fails the build if any route that reads its own body is not. The backup file inside a restore is a single text field that this screening does not open; the restore reads it itself and keeps only the fields each entry is allowed to have.

- **The server's request log can no longer record eight more kinds of secret, should request bodies ever be logged.** Password-reset, email-verification and unlock links (`token`), the signed two-factor challenge (`tempToken`), two-factor and backup codes (`code`), the vault key wrapped under your backup key in both backup-setup and backup-password-change requests (`bwkEncryptedVaultKey`, `newBwkEncryptedVaultKey`), the backup key itself as re-wrapped under a new backup password (`newEncryptedBWK`), the interrupted-rotation key a password change carries across (`newPendingEncryptedVaultKey`), and a restore's whole backup file (`data`, which carries your wrapped vault key inside it) are now redacted like passwords already were. Request bodies are not logged by default. The list is now checked against every request the server accepts, so a new field cannot be added without deciding whether it is a secret.

- **The key derived from your master password can no longer be copied out of the page.** It was created exportable, so script running in the page could take a copy of it, and rotating your vault key would not have retired that copy: the new vault key is sealed under that same key and the server hands the sealed copy to every sign-in, so a copy opened it too, until the master password changed. The browser now holds it as a key it will use but never reveal.

- **Decrypting no longer lets an encrypted file or a stored two-factor secret dictate how much work the decryption does.** Both formats record their key-derivation settings in bytes that are read before the password can be checked, so a tiny crafted `.enc` file could previously demand enough work to freeze a browser tab for a very long time. The cryptography library is now `@hiprax/crypto` 1.9.0, which checks those settings against a fixed budget before deriving any key, on the file tool and on the server's two-factor secrets alike; every file and secret H-Vault itself has written sits well inside that budget and still opens. The upgrade changes no stored byte: existing files and secrets are read exactly as before.

- **Dependency install scripts now have a recorded review policy.** The root `package.json` records an `allowScripts` policy that approves the two install scripts the tooling needs, each pinned to the reviewed version, and denies the rest, including an install-telemetry script that `scarfSettings` now also opts out of. Current npm releases treat the policy as advisory and later ones enforce it; production images already installed with scripts disabled.

- **Outgoing email now goes through Nodemailer 10 (was 9).** Every email the server sends now goes through Nodemailer 10.0.10: the verification, password-reset, unlock and registration-attempt messages, and the backup emails that carry your encrypted backup file. It parses recipient addresses and mail-server replies in linear time and keeps line breaks and control characters out of the boundaries of a message with an attachment. What is sent, how it is addressed and the email settings in `.env` are unchanged, and a send that fails is still reported, never raised.

## [0.13.0] - 2026-09-21

### Added

- **The password generator can now guarantee how many of each character type a password contains.** Sites that demand "at least two digits" or "at least one symbol" were impossible to satisfy reliably, because the generator drew every position independently and honoured no requirement at all: a 20-character password over the full pool came out with no digit at all about nine times in every hundred. Each enabled character type now has a minimum you can set, up to five, and the generator guarantees it. It does so without the usual sleight of hand. It does not generate a password and then overwrite a character, and it does not place the required characters first and shuffle, because both of those quietly distort which passwords are possible and neither can say how strong the result is. Instead it counts exactly how many passwords satisfy your settings and picks one of them uniformly at random, which means every allowed password remains equally likely and the strength figure beside it is the true one.
- **The generator remembers your settings.** Your length, character types and minimums can be stored on your account with **Save as my default**, and the generator opens with them next time, on any device you sign in from.
- **You can now get your codes out of Google Authenticator.** It offers no export file at all: the only way out is a set of QR codes shown on the phone, meant to be scanned by another copy of the same app, and it blocks screenshots so you cannot even photograph them from the device itself. **Import from Authenticator**, under the tools in the sidebar, reads those codes with your webcam. A batched export is several codes in sequence and it tracks which parts it has, in any order you show them, refusing to mix in a part from a different export. Every account it finds is listed with a live code beside it, so you can check one against your phone before trusting it. Nothing is attached to a login for you, deliberately: matching an imported code to a vault item by name is guesswork, and a code attached to the wrong account is worse than one not imported, because it looks right until the day it does not. You place each one yourself, by copying the key, creating a login from it, or choosing a login from a searchable list that shows the username beside the name so three accounts at the same provider are distinguishable. Logins whose stored data could not be decoded are left out of that list rather than shown and disabled, because writing to one would overwrite what is in it. Adding a code to a login that already has one keeps the old code in a hidden field by default, since a key cannot be recovered once it is gone. The whole decoded set can be saved into your encrypted documents in one action, written as ordinary `otpauth://` links so the file is usable anywhere rather than only here, and there is deliberately no plain download. If your camera is missing, refused, busy with a video call, or simply too coarse to read a dense code, the page says which of those happened and what to do about it, and pasting the export link or reading a photo of the code work just as well. Codes from any other service scan too, and the login form now has a **Scan QR code** button beside its TOTP field for exactly that.

### Changed

- **The strength readout now tells you what your requirements cost.** Requiring characters can only ever make a password weaker, never stronger, because it rules possibilities out; the near-universal belief is the opposite. When any minimum is set, the generator now says how many bits of strength it costs, and the bits figure beside the meter is the exact strength of the passwords your settings actually allow rather than of the ones they would allow without the requirements. For the shipped defaults at the default length this is about a seventh of one bit, and the displayed figure does not move; at a short length with heavy requirements it is large, and the meter is now able to fall to show it.
- **The generator refuses to generate rather than substituting something weaker.** Turning off every character type used to quietly produce a lowercase-only password, which is not what was asked for and is considerably weaker than it looks. It now says that at least one type is needed, and asking for more required characters than the password has room for says so too.

### Fixed

- **Two-factor codes now appear for accounts where they previously showed an error.** An item's code tile refused two things it should always have accepted, and both are shapes this app itself produces. The first is the ordinary 16-byte secret most services issue, which is 26 characters long and was rejected for having a length the old check misread as malformed. The second is a full `otpauth://` link, which every importer stores as-is and which this app's own export writes out, so exporting a vault and importing it back broke every code tile it touched. Both now work, and a link's own settings are honoured rather than assumed, so a service using a stronger hash, eight-digit codes or a different refresh interval produces the right code instead of a plausible wrong one. Counter-based links, which cannot be generated from a stored value, now say so instead of silently producing a code that never matches.
- **Your generator settings can no longer come back as missing.** Accounts created before these settings existed had nothing stored for them, and the profile response passed that absence straight through, so a client asking for them got nothing where it expected a value. They are now filled in from the defaults, and a stored value outside the range the generator can work with is brought back into range on the way out rather than rejected.

### Security

- **The QR decoder never runs in the page that holds your vault key.** Decoding a camera frame means handing third-party code the one kind of input this app takes from outside the machine, so it runs inside the same isolated document the file viewer uses: a sandboxed frame with no vault key beside it, no session, no storage and no network. The payload is then read by this project's own parser, which is bounded at every step, refuses a payload that is too large or too deeply nested, refuses an unknown hash algorithm rather than quietly assuming the common one, and is checked against arbitrary bytes on every run of the test suite, including a check that no error it can produce contains any part of what it was reading. The decoded keys are held in one place and overwritten with zeros when you leave the page, lock, sign out or start over. `SECURITY.md` records what that frame can still do and why the alternative is worse.

- **`Math.random` is now rejected across the codebase by the linter.** It is not a cryptographically secure source: its output is predictable from a handful of observations, which is exactly the attack a password manager must not be open to. Nothing used it, and now nothing can start to without the check failing, including the two spellings that a simple search for it would miss. All random choices about secret material go through one audited module that draws from the platform's cryptographic generator, rejects biased draws rather than folding them, and throws rather than falling back to anything weaker when that generator is unavailable.

### Added

- **You can now take every document out in one action.** Documents are the one thing an encrypted backup does not carry, so until now the only way to get a copy of them off a server somebody else runs was to download them one at a time. **Download all**, on the Documents page, saves every document the list is showing — which means the folder, favorites, trash and search filters decide what is exported, and is how a library too large for one run gets broken into pieces. All are corrected, and the number in each is now checked against the one list that defines which views are scanned, in both directions: adding or removing a view without moving the prose with it fails the documentation check, and so does a sentence this check can no longer find.

- **Every setting the server reads is now guaranteed to be documented in `.env.example`.** That file is the deployment's one configuration file and the only place an operator is told a variable exists, and nothing compared it with the settings the server actually accepts, so a new one could exist, have a default and change behaviour while being impossible to discover. The two are now checked against each other in both directions: every declared setting must be documented, and every variable documented there must be read by something — the server, the Docker stack, or the logger — with the file that reads it named and that claim checked. Nothing was missing today; the check is what keeps it that way.

- **The end-to-end suite now runs on two browser engines, and setting it up needs a second browser.** The clipboard-hygiene and auto-lock journeys — the two whose answers depend on what the BROWSER does rather than on what this application does — now run on Firefox as well as Chromium, as their own attributed leg of the same gate. The rule they turn on is genuinely different between engines: Chromium decides whether a page may write to the clipboard from a permission and from whether the window is in front, while Firefox and Safari require a fresh user gesture for every single write. That is why this app keeps a copied secret pending and retries the erase at your next click instead of assuming it worked — and until now that retry had only ever been exercised against a stubbed browser. It is now driven by a real refusal from a real engine, and measuring it turned up something the code did not claim: Chromium refuses the timed erase as well, with the permission granted and — asserted in the same test — the page in front, so the behaviour that was written down as a Firefox and Safari peculiarity is what both engines this project tests on do. Nothing about the application itself changed. Running the suite locally now needs `npx playwright install --with-deps chromium firefox`; installing only Chromium fails exactly as an empty browser cache does, and the release workflow installs both.

- **Every operation in the published API description now has a name, and the description says where to take a problem.** The document this server serves at `/api/v1/docs.json` is what generates a client library, and an operation with no `operationId` is one whose method name the generator has to invent — so the same endpoint could come out as `getVaultItemsIdGet` in one tool and something else in the next, and a rename anywhere would silently rename a method. Fifty-three of the sixty-nine operations had none; all sixty-nine do now, each spelled so that a generator can use it verbatim, and no two the same. The description also carries contact details for the first time, pointing at the project's issues page — a security problem still goes to the private advisory that `SECURITY.md` describes and never to a public issue. Nothing about any endpoint's address, request, response or authentication changed, and every name is checked to be present, unique, usable as a method name, and tagged with a section the document actually declares.

- **The Docker images identify their runtime user by number and probe their own health without a shell.** The API and index-creation images said `USER node`, while every temporary filesystem the stack mounts for them is pinned to `uid=1000` — the same account written two ways, and a mismatch between the two is the failure mode where the container starts once and then silently refuses to come back. Both now say `USER 1000:1000`, which selects the identical account with the identical home directory, and the Nginx image says `USER 0` for its package-upgrade step to match the `USER 101` it drops back to. The API image's built-in health probe is now given as a list rather than a command line, so it no longer starts a shell every thirty seconds merely to start the check inside it. The Nginx image's package upgrade and its worker-count edit are now one step, in that order, because an upgrade of the Nginx package rewrites the file the edit changes — an ordering that used to depend on the two steps staying adjacent.

- **Most of the libraries this application ships have moved forward a release.** The HTTP client, the validation library, React and the router, the form library and its resolvers, the state store, the icon set, the list virtualiser, the one-time-password library, the rate limiter and the database driver all moved forward within the version they were already on, and so did the toolchain that builds, formats, lints and tests the project. No major upgrade was taken, no interface changed, and `npm audit` reported no advisory either before or after — this is currency rather than a fix, and it is worth taking on its own schedule so that the day an advisory does appear the jump is a short one. Three were deliberately held back at that point even though a newer release exists: the mail sender and the object-storage client, which were for a later pass, and the file-encryption library — that one owns the format of the `.enc` files you have already saved and the memory profile they were encrypted under, so moving it is a compatibility review rather than a refresh. One thing you can actually see moved with it. When you ask the uploader to format or repair a document, the review panel names the tool that rewrote your bytes and that name is sealed into the document's own record; it now reads `prettier 3.9.6` where it read `3.9.5`. That release changes only how Prettier formats JavaScript and TypeScript, neither of which this application ever formats, so your JSON, JSONL, Markdown and YAML come out byte for byte as they did before. The first page a visitor downloads grew by about 23 KB uncompressed, roughly two thirds of it the validation library's own growth and most of the rest the HTTP client's, which leaves it comfortably inside the ceiling the build enforces; the ceiling itself was not moved. Two icons were renamed upstream and both keep the artwork, the name this application imports and the style hook it always had. Running the end-to-end suite locally now needs its browsers re-fetched with `npx playwright install --with-deps chromium firefox`, exactly as a first checkout does. The mail sender did not stay held back: an advisory landed against it before this release shipped, and it moved to the fixed version — see Security, below.
- **A breach lookup no longer walks the whole cached-response table on every insert.** The server keeps recently fetched breach ranges in memory, bounded by a count and a byte budget, and evicts an entry whose hour is up in preference to the oldest one. Finding that expired entry meant scanning every cached response, on every insert, once the cache was full — and when nothing had expired yet, that scan found nothing, so checking a large vault paid for a full walk once per range it fetched. The cache now records the earliest expiry it is holding and skips the scan entirely while that moment is still in the future. Which entry gets evicted has not changed.

### Fixed

- **The deepest gate in the project could never have been armed.** `test:mutation` changes the source code one edit at a time and asks whether any test notices; its floor lives in `.testfortress/baseline.json`, and until that floor exists the gate deliberately fails rather than passing while measuring itself against nothing. The way out was documented in three places — the README, the gate's own failure message and the ledger entry tracking it — as running the campaign and then accepting the result. That could not work: accepting only ever moved numbers the baseline already held, so the first campaign would have been followed by an acceptance that silently recorded nothing, and the gate would have failed again for the same reason with hours of measurement thrown away. The acceptance step now has a flag for recording a measurement for the first time (above), the failure message names it, and the README passage that prescribed the impossible procedure is corrected. A second, quieter half of the same fault is fixed with it: the per-module mutation scores were only ever computed for modules the baseline already listed, so on a first run there were none to list and a module added to the list later would never have been measured either — they are now computed from the declared list of core modules as well, while a module the baseline still names goes on being required.

- **Four controls that a screen reader had no name for.** Each of these is a button or a field whose only visible content is an icon or a slider, so the name a screen reader announces has to be written down — and on four of them it was not, which leaves someone navigating by voice or by keyboard being told only "button" or "edit text". The show/hide-password control on the password-reset page, which sits beside the field where you type your new master password, now announces "Show password" and "Hide password" exactly as the same control on the sign-in and registration pages already did. The auto-backup switch on the backup settings page now takes its name from the words already printed next to it and also reads out what they explain, so its purpose no longer depends on being able to see where it sits. The backup schedule hour — a bare number field with no placeholder to fall back on — and the file picker on the restore panel, whose caption was merely printed above it rather than attached to it, are now properly labelled. Nothing about how any of the four behaves has changed.

- **Two lines on the "Leave H-Vault" page were too faint to read.** This is the page that exports your vault as an unencrypted file, so it is the page whose warnings matter most, and two of them did not meet the contrast requirement for text of their size on the surface each is actually painted on. The label on the "Prepare plaintext export" button was white on an amber only bright enough for much larger text, at 3.19:1 against a 4.5:1 requirement. The sentence "This file is UNENCRYPTED plaintext", which is the first thing the page says, sits on a faintly red-tinted panel and measured 4.43:1 there; it clears the requirement on plain white, which is why it looked safe, and the tinted panel is the only place it is ever drawn. Both are one shade darker now, at 5.03:1 and 5.97:1 respectively, and so are the two amber lines further down the page that report skipped items, which had the same problem at the same 3.20:1. The colours are otherwise unchanged, and the amber is deliberate: this action is dangerous without being destructive and must not look like the red used for deletion.

- **The audit log's coloured labels have room to spare now.** Each entry carries a badge tinted by what it records — a green "Login", a red "Failed Login", an amber "Backup Code Used" — and the text on those tints sat on the line rather than above it: measured off what the browser actually paints, green was 4.496:1 against a 4.5:1 requirement and amber, orange and yellow cleared it by between two and nine hundredths. That is a margin decided by rounding rather than by choice, so every one of them is a shade darker and none now measures below 6.36:1. Nothing else about the badges changed, and the dark theme's versions, which were already comfortable, are untouched.

- **A folder that has sub-folders is no longer one control pretending to be two.** Each folder in the sidebar is a button you click to open it, and a folder with sub-folders carries a second, smaller button that expands and collapses them. That second button was drawn INSIDE the first, which is not something a browser or a screen reader defines: the platform treats the whole row as one flat control, so anyone navigating by keyboard could land on the expander and be told nothing at all about what they had reached. It is now drawn beside the folder button rather than inside it. Everything the row does is unchanged, including clicking to open, right-clicking for the menu, dragging to reorder, Ctrl+Up and Ctrl+Down, the colour bar, the selected highlight and the drop-target ring, which still span the whole row.

- **A browser-storage transaction that ended without reporting an error left the app waiting for it for ever.** Both places this app stores data in the browser — the offline copy of your vault, and the saved results of a Vault Health scan — waited for a storage transaction to either finish or fail, and a transaction can do neither: it can simply be cancelled, which is what happens when a write fails at commit time rather than while it is being written. Nothing was listening for that, so the wait never ended. For the health results that was the worse of the two, because every save and the sign-out cleanup share a single queue: one cancelled write stopped all of them for as long as the tab stayed open, and signing out — which waits for that cleanup — never completed. Both now treat a cancelled transaction as the failure it is, which for the health results means the save is quietly skipped exactly as any other storage failure already was.

- **A failed save of the offline copy of your vault always reported the reason as unknown.** The app classifies these failures so it can tell a full browser storage apart from a browser that is blocking storage outright, but for every failure that happened while writing — which is every failure that a full storage can cause — it looked for the reason in a place the browser has not filled in yet at that moment, found nothing, and settled for a generic one. The reason is now read from where the browser does put it, so the two causes a person can act on are distinguished from each other and from everything else. On its own this was invisible; it is what makes the new offline-storage notice able to name a remedy instead of shrugging.

- **A momentary failure to reach the server could quietly stop a vault-key rotation from re-keying your documents.** Whether this server stores documents at all is read from it once and remembered for as long as the tab is open, and a request that failed was remembered as "it does not" — which is right for hiding a menu entry and wrong for anything that acts on it. A rotation asks the same question to decide whether to re-key every document you hold, so one failed request, on any page, at any earlier point in the session, made every rotation afterwards claim you had no documents. The server refuses that outright, because a rotation has to name every row an account holds — but the reason it gave named a pending deletion or missing storage, neither of which had happened, and nothing short of reloading the page cleared it. The rotation now re-reads that answer at the moment it needs it, and when the server does not answer it stops before sending anything and says so, which leaves your vault key exactly as it was and can simply be tried again. A successful re-read also corrects the remembered answer, so a document store that an earlier outage had hidden is offered again by the next screen that asks for it.

- **Emptying the document trash while the trash was still loading no longer shows you an empty trash.** When the storage service cannot delete every file, the trash is re-read afterwards so that what is on screen is what is really still there — the message says as much. If that re-read happened while the list was already loading, it was answered by the load that was already running, whose result had just been discarded as out of date, so nothing was written and the trash appeared empty while the documents were still on the server and still counted against your storage. It now always performs a genuinely fresh read. This mattered more than it looks: emptying a trash against a storage service that is down stops after several refusals and reports them, so the re-read is the ordinary path during an outage rather than a rare one, and the documents it brings back include the ones the server never got to — which carry no marker of any kind and would otherwise have been invisible until the page was reloaded.

- **A rename is no longer applied to the wrong document if the server answers about another one.** The response to a rename is checked against the document that was renamed before it is used, which the other document-editing paths already did. Without it, a mismatched answer left the renamed document untouched and rewrote a different one instead — with a row whose keys belong to that other document, which this browser may be unable to open, so a perfectly good document could be left showing as unreadable and refusing to be renamed.

- **`npm run build` could produce nothing at all, and still report success.** A TypeScript build that keeps incremental state does not check whether the files it previously emitted still exist, so deleting a package's `dist/` while that state survived — which is exactly what `npm run clean` did — left the next build exiting 0 having written no output. The shared package's state now lives inside the directory it describes, so removing that directory is always a correct rebuild from scratch, and `npm run clean` clears the remaining state files as well.

- **Retrying a vault-key rotation can no longer run it twice.** A rotation may carry a key that identifies the attempt, so a client that retries after a timeout is answered with the original result instead of rotating again. That check read the account as the request arrived, before the rotation was claimed — so a retry sent while the original was still working read a key that had not been recorded yet, waited its turn, and then rotated a second time. Nothing was corrupted, because a retry carries the same re-encrypted data as the request it repeats, but the account's vault-key generation advanced twice and the second run was recorded in the audit log as a rotation nobody asked for. That generation is what an upload in progress is checked against, so an extra step could refuse a document whose key was in fact current. The check is now answered after the rotation is claimed, where the answer cannot be stale.

- **Uploads started at the same moment can no longer carry an account past its document limit.** Opening a transfer counts the documents already stored, counts the transfers already running and checks the storage quota, and then records the new transfer — but nothing kept two of those from happening at once, so several uploads started together all read the same counts, all passed, and all went ahead. The advertised limit was never the real ceiling: the count is only checked when a transfer opens, so an account was always allowed to finish slightly over it, and the size of that overshoot was supposed to be capped by the limit on simultaneous transfers — which was itself decided the same racy way and so capped nothing. Enough uploads begun together therefore pushed an account past the number of documents a vault-key rotation is allowed to name, which would have left it unable to rotate its vault key ever again, with permanently deleting documents the only way out. Those three checks and the record they write are now decided one at a time per account, so the overshoot is bounded as it was always meant to be. An upload begun while another is still being opened for the same account is asked to retry rather than failing, and the app reports that message to you; because it sends one file at a time, seeing it means confirming a second file within the fraction of a second the first one takes to start.

- **Emptying the document trash, and the nightly purge behind it, no longer run for hours against storage that is down.** Both walk the trash one document at a time, deleting the stored file and then the row that holds its only key, and both deliberately count a file they cannot reach and carry on — which is right for one unreachable file and wrong for a storage service that is refusing everything. Each attempt costs about fifteen seconds when the service is unreachable, so a full trash meant a request left open for hours after the browser had given up, and a nightly job still running long after the fifteen-minute claim that was supposed to keep a second copy of it from starting had expired. Both now stop after several refusals in a row and report exactly what they attempted, rather than claiming the whole trash. Nothing is destroyed either way and nothing is lost: the documents they reached keep the marker that has the hourly collector finish them, the documents past that point are left completely alone and still in your trash, and the Documents page re-reads the trash whenever anything failed, so what you see is what is really still there. The message shown after emptying the trash no longer promises that everything it did not delete will be cleaned up automatically, which was true of the files it tried and false of any it never reached; it now points you at the refreshed list instead. A single unreachable file is unchanged — the walk finishes and reports it, exactly as before.

- **A document that was still being formatted no longer follows you to the next file you choose.** Ticking Format or Repair prepares the file in your browser and shows you exactly what changed before anything is uploaded. Nothing cancelled that preparation, though, so choosing a second file while the first was still being worked on left the first one's result to arrive afterwards — and it arrived as a review of a file that was no longer on screen, offered against the one that was. Confirming it uploaded the first file's contents under the second file's name, and the record of what had been rewritten, which includes a fingerprint of the original, then described a document that had never been uploaded at all. The same went for a failure: a syntax error in the file you had moved on from was reported against the file you had moved on to, which had not even been read. A result now belongs to the selection that asked for it, and one belonging to any earlier selection is discarded. A result that arrives late while a second file is being prepared no longer takes the second one's place either, so a review you are part-way through reading stays where it is.

- **A file that grows past the server's size limit while being formatted is now refused before it is sent.** The size check ran on the file you chose, but what gets uploaded after a format or repair is the rewritten version — and re-indenting a compact document can easily double it. A file that was comfortably inside the limit when you picked it could therefore be outside it by the time it was sent, and the only thing that noticed was the server — which refused it, correctly and with its own message naming the limit, but not until after you had confirmed the rewrite and the panel had already cleared your selection, so the answer arrived beside neither the file nor the comparison you had just approved. The review now checks the rewritten file too, and where it does not fit it says so in the same terms the first check uses, naming the limit and the size, with the comparison still on screen and the original file still offered unchanged. Servers that advertise no size limit are unaffected.

- **Clicking Retry twice on a failed upload no longer stores a document nobody can open.** The Retry button had no busy state, and the upload's own guard against a second attempt did not take effect until the app had asked the server which parts it already held — a full round trip. A second click inside that gap started a second transfer of the same file, and the two then shared one cancel button between them: cancelling reached only the later transfer, while the earlier one carried on and finished the file with a key that had already been erased. The document appeared in your list with its right name and size, counted against your storage, and no password would ever open it — and, because rotating your vault key stops at the first document it cannot re-wrap, one of them blocked every future rotation of the account until it was permanently deleted. A resume that is already being prepared now refuses a second one outright, and the button says "Retrying" and stops accepting clicks while it waits, so the second click no longer happens in the first place. A resume that fails again can still be retried, as many times as you like.

- **Renaming a document while you are looking at it no longer replaces the preview with an error.** Every document is shown inside its own isolated frame, and the file is handed to that frame once, at the moment the frame reports it is ready. A document's name decides how it is displayed, so renaming `notes.md` to `notes.markdown`, or a `.txt` to a `.log`, changes the instructions the frame needs — and the viewer tried to give the new instructions to the frame it already had, which has no way to ask for them a second time. After ten seconds of silence the preview you were reading was replaced by "The document preview did not load." A rename now builds a fresh frame, exactly as opening a different document or switching between light and dark already did.

- **A document with nothing visible in it is now shown as an empty page instead of reported as broken.** A Markdown file whose only content is an HTML comment, and a stored web page with an empty body, both end up with nothing left to display once comments, scripts and styles are removed — and the viewer answered "The document could not be displayed." for both, which reads as a damaged or unreadable file. Each now renders as what it is: an empty page, with the stored-web-page notice still shown above it. An empty file of source code likewise keeps the styling every other code file gets, rather than quietly falling back to plain unstyled text.

- **A very wide spreadsheet no longer freezes the tab it is previewed in.** A `.csv` or `.tsv` preview is drawn as a table, and every row is padded out to the width of the widest one — so the number of cells on screen is the row count multiplied by the column count, while only the row count was ever limited. The width came entirely from the file: a 25 MB line of commas is well inside the size a document may be previewed at and asks for twenty-six million cells in a single row, and one unusually wide row anywhere in an otherwise ordinary file widened every other row to match. The table is built as soon as the document opens, not when you switch to it, so the tab stopped responding on opening the file, and nothing said why — the notice above the table counted rows, and no row had been dropped. A preview is now limited by its total number of cells as well as by its width, and the notice names both dimensions: it says how many rows of how many, how many columns of how many, or both, whichever were actually cut. A narrow spreadsheet is unaffected; a wide one may now show fewer rows than before, and says so. The full file is a download away, as it always was.

- **A responsive image is now explained instead of just appearing broken.** A stored document may reference an image held elsewhere on the internet, and those are never fetched — doing so would tell whoever wrote the document that you opened your copy — so the viewer shows a notice saying exactly that. The notice was raised only for a plain image tag, and missed the `<picture>` element, whose alternatives live in a list of candidates rather than in a single address. A README written that way showed a broken image with no explanation, which reads as a broken viewer. Every element that names an image is now checked, each candidate within a list is checked separately, and each address is resolved the way the browser resolves it rather than matched against a list of prefixes — which had also missed several perfectly valid spellings of a remote address. Nothing about what is fetched has changed: the request was already refused, and still is.

- **A link to an anchor with an unusual character no longer stops the links below it working.** A document may link within itself — a contents entry, a heading anchor, a footnote — and the viewer resolves those itself rather than handing them to the app. Resolving one meant decoding it, and a link written like `#%`, which is perfectly ordinary to write, is not a valid encoding: decoding it failed outright, and the failure escaped the handler that every link in the document shares. Such a link now scrolls to an anchor of that exact name if the document has one and does nothing if it does not, which is what every unresolvable link already did, and the links around it are unaffected either way.

- **The README's count of accepted static-analysis findings is now the real one.** The security-tooling section publishes how many error-severity findings the CodeQL gate accepts rather than fails on, with the reason each one was reviewed and kept, because that list is the answer to why a security gate passes with findings in it. It said 24 accepted and 20 of the commonest kind, over a recorded set holding 27 and 23: the recorded set is regenerated by a command whenever the code moves, and the prose only when somebody remembers it. Both figures are corrected, and the whole breakdown — the total, every rule named and its count — is now compared against that file in both directions, so a rule accepted with no stated reason fails as loudly as a wrong number. One of the stated reasons was also wrong about the code it described, and now says what the app actually does. No finding was added, removed or re-reviewed; what was wrong was the description of them.
- **The deepest gate copied three gigabytes of scratch space into every one of its sandboxes, and on some machines that killed it outright.** `test:mutation` works by copying the project into a private sandbox per worker and rewriting one line at a time. The list of things not worth copying named the build output, the coverage reports and the git history, but not `.cache/` — the local pipeline's own scratch directory, which on any machine that has run the static-analysis gate holds a CodeQL bundle and its database, measured here at 3.1 GB. That was copied once per worker, three times per package. It is now excluded, alongside the others: the same run of one package's leg went from 32 seconds to 13, and the crash it caused on a populated cache (`EISDIR` on the bundle directory) is gone. Nothing about what gets mutated changed, and the gate reports the same 2,469 mutants at the same score.

- **The end-to-end suite's "are we in the vault?" check could not tell a locked vault from an unlocked one, and one test paid for it with a five-minute timeout.** Locking does not change the address, so that check looks for the sidebar's **Lock Vault** control, which only the unlocked screen has. It looked for it by pattern rather than by exact name, and the unlock screen's own button is called **Unlock Vault** — which contains those words — so the check passed on the locked screen and proved nothing. On a busy machine the suite therefore moved on while a key derivation was still running, the next step clicked the unlock button instead of locking, and the step after that waited out its whole budget for a button that had by then gone. The check now matches the exact name, the three places that had written it out for themselves share one definition, and a test asserts both halves: that the control really is absent while the vault is locked, and that the loose pattern really does match the wrong button, so nobody restores it as a simplification. Two sentences describing the mutation gate's scope also said "six core modules" where there are seven, and both are now checked against the list itself.

### Security

- **A file uploaded from a browser tab that was open when you rotated your vault key is no longer stored unreadable.** Rotating the vault key does not sign out your other sessions, so another tab can go on holding the key it was given when it signed in. Uploading a document from such a tab used to store its key under that superseded vault key while the server, comparing its own version number against itself, saw nothing wrong: the document then appeared in your list and counted against your storage, and no password would ever open it. It was worse than one lost file, because rotating the vault key stops on the first document it cannot re-wrap — so a single such upload blocked every future rotation of the account until that document was permanently deleted. Signing in now tells the browser which generation of the vault key it received, an upload says which one it actually used, and a mismatch is refused and recovered from automatically: the browser fetches the current key, re-wraps the document's key and finishes the upload without re-sending a byte of the file. A version the account has never reached is refused as well, and says so rather than reporting a rotation that did not happen.

- **A single-use backup code no longer registers the device as trusted.** Signing in with "Remember me" and completing two-factor authentication used to register the browser as trusted whichever of the two credentials was presented. A code from your authenticator app shows the second factor is on the device in front of you; a backup code shows the reverse, because the batch of eight is kept where that app is not — printed, in another password manager, mailed to yourself. So one line off that sheet bought a 30-day skip of the second factor on that browser, and, because each recognised-device sign-in starts a fresh 30-day session while the trust record keeps its own expiry, up to 60 days without a code from the app ever being asked for again — with nothing in the audit log to show for it. A backup code now signs you in, still gives you the full remembered session, and registers no device; the next sign-in on that browser asks for a second factor as it should. Signing in with a code from your authenticator app is unchanged. A device already registered this way before the change keeps that trust until it expires on its own — revoke it from the Sessions page if you would rather not wait.

- **A malformed cookie no longer breaks six sign-in and account endpoints, or half-disables two-factor authentication.** Cookie values are decoded before they reach the application, and a specially shaped value arrives as a number or an object rather than the text that was sent. Six places read a cookie as though it were always text: refreshing a session, signing out, signing out everywhere, listing your active sessions, turning off two-factor authentication, and the recognised-device check during sign-in — that last one being the only one that reads the remembered-device cookie rather than the session cookie. Sending such a value made each of them fail outright with a server error: on session refresh from any client at all, since that endpoint needs no credentials, and on the others from anyone who could already reach them. Turning off two-factor authentication was the damaging one: it recorded the change and then failed, leaving the account with two-factor off while every session and every remembered device from before the change stayed valid and nothing was written to the audit log. A cookie the server cannot read is now treated exactly as an absent one, everywhere, and turning off two-factor authentication now reads everything the request carries before it changes anything, so nothing you send can interrupt it between recording the change and revoking what that change invalidates.

- **Signing in again no longer clears the two-factor lockout count.** One failed-attempt counter serves both sign-in steps, and it is the only _per-account_ limit on the two-factor code — the other limits on that step count per address, not per account. It used to be cleared the moment the password was accepted, which is before the code is even asked for, so anyone who already held the master password could re-enter it between batches of wrong codes and reset the count indefinitely: ten guesses per half hour became roughly a hundred and eighty per quarter hour, and on a self-hosted instance not running in production mode, where the rate limiters are inactive, it became unlimited. The count is now cleared only when a sign-in actually completes — an ordinary sign-in with no second factor, a recognised trusted device, or a verified code — and a two-factor prompt that is issued and then abandoned clears nothing. A lockout you have already waited out is still cleared by entering your password, for accounts with a second factor as well as without, so a code mistyped after the wait does not immediately re-lock you.

- **A cross-site-request token is now accepted in exactly one form.** Every state-changing request carries a short signed token that proves it came from the app rather than from another site. The check compared only the first 64 characters of that token's signature and then required the rest to be merely non-empty, so a genuine token with any extra characters stuck on the end was still accepted — one issued token quietly became an unlimited family of different strings the server would take. Forging one was never possible, since the signature still had to be right, but a token meant to identify a request must have a single valid form, or it cannot be relied on anywhere it is compared or recorded. The signature must now be exactly its own length, and anything longer or shorter is refused.

- **A breach lookup can no longer be used to exhaust the server's memory.** Checking whether a password appears in a known breach is the one request this server makes to an outside service, and its reply was read in full with no ceiling on how large it was allowed to be. A reply is normally around a hundred kilobytes; nothing stopped an unhealthy or hostile service on the other end from sending gigabytes, and the batch check opens eight of these at once. Replies are now capped at one megabyte — roughly ten times the largest legitimate one — and the connection is dropped the moment a reply goes over, before the excess is ever held in memory. A reply that is refused is reported as a failed check, exactly as a timeout already was, and never as "this password appears in no breach". The stored copy of a breach range carries the same limit.

- **The mail sender has been moved to the release that closes an advisory against it.** The library this server uses to send verification, password-reset and unlock email published a fix for a flaw in one of its older calling conventions: an application that switches on the library's file and URL sandbox, and then asks it to resolve message content through the three-argument form of that call, silently loses the sandbox and can be steered into reading a local file or fetching an internal address. H-Vault does not do either of those things anywhere: it never enables those two options and never makes that call, and the only attachment it ever sends is a backup file it has already built in memory, so no version of this application was exposed. The library has been raised to the fixed release regardless, because the previous release deliberately held this one back for a later pass and an advisory is what that pass was waiting for. Nothing observable in this application changed with it: the releases in between altered how the library encodes header parameters and parses address lists, neither of which this server exercises — it sends one plain recipient at a time and the one attachment it ever builds has a plain ASCII name. The test runner was moved for the same reason, to the release that closes a path-traversal advisory in its mocking helper; it never ships to you and is listed only so the record of what moved is complete. Re-resolving the dependency tree around those two moved a handful of indirect packages within the versions they were already allowed: the only two in the shipped server are the header parser that reads the `Content-Type` of every request body, which went up a minor version, and the version-comparison helper used by the token library, which settled a patch lower than it had been sitting after a duplicate copy was collapsed away. Neither carries an advisory at any severity, no interface changed, and nothing the browser downloads moved at all. `npm audit` now reports no advisory against this project at all, development tooling included.

## [0.10.0] - 2026-09-03

### Added

- **Configuration for an optional encrypted document store**, off unless it is configured. Four new connection variables (`S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`) are validated all-or-none, exactly like SMTP: set them all and the feature is available, leave them all empty and nothing changes, and a partial set is a startup error in production rather than a half-enabled feature. Alongside them: `S3_REGION` (default `us-east-1`), `S3_FORCE_PATH_STYLE` (default on, because virtual-host addressing needs DNS an in-stack service does not have), `MAX_DOCUMENT_SIZE_MB` (1-1024, default 100), `DOCUMENT_STORAGE_QUOTA_MB_PER_USER` (1-1048576, default 2048, and it must cover the size cap or the app refuses to boot), `DOCUMENT_UPLOAD_TTL_HOURS` (1-168, default 24) and `DOCUMENT_ALLOWED_EXTENSIONS`, an advisory allowlist enforced in the browser because the server receives ciphertext and cannot see a filename. In production a plain `http://` endpoint is accepted only for a loopback address, an RFC 1918 private address or a single-label host such as an in-stack service name, so bucket credentials cannot cross a network in the clear by accident. All of them are documented in `.env.example` and the README, together with `S3_RPC_SECRET`, which only a self-hosted storage container reads.
- **The first four endpoints of the encrypted document store**, all under `/api/v1/documents` and all available only where an operator has configured object storage. `POST /uploads` opens a transfer and returns the id the browser binds its encryption to before it seals a byte; `GET /uploads` and `GET /uploads/:id` report the transfers in progress and the parts the server already holds, so an interrupted upload can resume without re-sending them; `DELETE /uploads/:id` cancels one and releases what the storage engine was holding. Opening a transfer is refused, with nothing left behind, when it would exceed the size cap, the document count, the number of transfers one account may run at once, or the storage quota — which counts trashed documents and the declared size of transfers already open, because both still occupy space.
- **Uploading a document's bytes**, one sealed segment at a time, through `PUT /documents/uploads/:id/parts/:partNumber`. The body is the raw ciphertext as `application/octet-stream`; the request must declare its length, and it carries a SHA-256 of the segment that the server recomputes over the bytes it actually received, so a part corrupted in transit is refused rather than stored. Every part except the last must be exactly one full chunk: a short middle part is accepted by S3-compatible storage engines and would shift every later segment boundary, leaving a file that uploads successfully and can never be opened again, so the server is what refuses it. Re-sending a part replaces it instead of counting it twice, which is what makes a retried part safe, and a part offered against a transfer that has expired or that belongs to another account is refused without storing anything. The number of parts being buffered at once is bounded per server process, so a burst of large uploads cannot exhaust the memory of a container running under a fixed limit.
- **`GET /config` now says whether the document store is available**, reporting `enabled: false` where no object storage is configured and, where it is, the size cap, the per-user document and byte limits and the advisory extension list the browser enforces. The block is absent altogether on a server older than the feature, so a client can tell an out-of-date server from an unconfigured one.
- **Three dedicated rate-limit budgets for the document store**, each keyed by account rather than by address so uploading files can never cost a sign-in, and none of them shared with any credential endpoint. The upload budget is flat; the part and segment budgets are derived from the operator's own `MAX_DOCUMENT_SIZE_MB` and allow for concurrent transfers and retried parts, so a large upload is never refused half-way through. Documented in the README's rate-limit table.
- **Finishing an upload**, through `POST /documents/uploads/:id/complete`. The server checks every part against the storage engine's own record of what it holds and works out the document's size and segment count from that record rather than from anything the browser claims, so a client cannot understate what it stored or leave a file framed in a way that would never open again; the storage quota is then re-checked against the bytes that actually arrived. The wrapped document key is sent again with this request, which is what makes a vault-key rotation that happens mid-upload cost one retried request instead of the whole file: the response says which key version is current, the browser re-wraps the key it still holds, and no byte is uploaded twice. Completing the same transfer twice returns the document the first attempt created rather than a second copy or an error, so a client that retried after a timeout is safe.
- **Five new audit-log actions covering documents** (created, updated, trashed, restored and permanently deleted), taking the log to 46 distinct operations. Reading or downloading a document is deliberately not audited: no read is audited anywhere in H-Vault, and one download is one request per segment, so recording them would bury every entry worth finding.
- **Reading documents back**, through five endpoints under `/api/v1/documents`. `GET /documents` and `GET /documents/trash` page through the active and the trashed lists (filter by folder or favorite, sort by created, updated or favorite, with the document id breaking ties so that a row can never slip across a page boundary between two requests); `GET /documents/usage` reports the count and bytes stored beside the operator's per-user quota and per-document size cap, counting trashed documents in both because they still occupy storage; `GET /documents/:id` returns one document's wrapped key, framing and sealed metadata. `GET /documents/:id/segments/:index` streams one sealed segment as raw bytes: the byte range is computed on the server from the document's own framing, never sent by the client, so a segment can only ever be read from the offset it was written to. Those responses carry `Cache-Control: no-store` and an exact `Content-Length`, so ciphertext is never cached and a truncated transfer cannot be mistaken for a whole segment, and a document whose stored contents have gone missing is reported as a plain 404 rather than as a download that silently fails.
- **Renaming, organising and deleting documents**, through five more endpoints under `/api/v1/documents`. `PUT /documents/:id` re-seals the metadata blob — the filename, the type, the tags and the note, all of which stay encrypted — and sets the favorite flag and the folder; sending `folderId` as null takes the document out of its folder. It cannot change a byte of the stored content or of the framing that describes it, and it cannot reach the wrapped document key or the storage address, because content is immutable after upload: a segment is never rewritten, which is what guarantees the encryption of two different files can never share a nonce, so replacing a document's bytes means uploading a new document. It is also the one write of ciphertext that is not refused while a vault key is being rotated, because the metadata is sealed under a key derived from the document's own key, which a rotation only re-wraps. `DELETE /documents/:id` moves a document to the trash, where it still occupies storage and still counts against the quota until it is permanently deleted, and `POST /documents/:id/restore` brings it back. `DELETE /documents/:id/permanent` and `DELETE /documents/trash/empty` destroy a trashed document and the whole trash respectively: each one marks the row, deletes the stored object and only then deletes the row, so an interruption at any point leaves a marker the hourly cleanup finishes rather than a file in the bucket that nothing names any more. Emptying the trash is bounded to what was in it when the request arrived, so a document deleted in another tab meanwhile survives, and it reports anything it could not remove rather than claiming success.
- **Rotating a vault key now re-keys documents too.** `POST /vault/items/bulk-reencrypt` accepts a `documents` leg alongside items and folders: one rewrapped document key per document, active and trashed alike. Only the 32-byte key travels — no file is read, re-uploaded or even touched — which is what keeps rotation possible on an account holding gigabytes. The leg is a full peer of the other two on both storage topologies: a document the request names but the account does not hold aborts the whole rotation before anything is written, and on a single-node deployment a failure part-way restores every document already rewrapped, so a rotation can never leave files sealed under a key the account no longer stores. The server also records which vault key an account is on, so an upload that was in flight across a rotation is refused with a conflict the browser recovers from by re-wrapping the key it still holds, rather than by sending the file again. Changing the master password does not move that counter, because it re-wraps the same vault key rather than replacing it.
- **A backup now records how many documents the account held.** Documents are deliberately not part of a backup: their bytes cannot fit a backup file, and metadata without bytes would restore entries pointing at files that are not there. So every backup — the scheduled email and the manual download alike — carries a small `documentSummary` line, and restoring a backup taken from an account that held documents now says so plainly instead of letting a restored account look complete. Older backups have no such line and restore exactly as before.
- **An hourly clean-up that reclaims storage nothing can name any more.** Three things can leave bytes behind in object storage: a transfer abandoned part-way, whose staging entry expires on its own but whose already-uploaded parts do not; a permanent deletion interrupted between removing the file and removing the entry; and a file whose entry was lost altogether, including one an account deletion could not reach because storage was unavailable at the time. The new job finishes all three, and refuses to touch anything it cannot prove is unreferenced — a file belonging to a document that still exists is never deleted, whether that document is active, in the trash, or part-way through being purged, and neither is one belonging to a transfer that could still be completed. It walks a bounded slice of storage per run and continues from where it stopped, so a large deployment is swept over successive runs rather than in one burst, and it stops early if the storage service starts refusing rather than spending hours retrying. It is scheduled only where object storage is configured.
- **`GET /api/v1/metrics` now reports object storage.** A one-off check at start-up confirms the configured bucket is reachable, and the result is reported as `storage: { configured, lastProbeAt, lastProbeOk }`. It never blocks start-up and never fails it: an unreachable bucket disables one feature, not the server. `GET /api/v1/health` deliberately says nothing about storage and never contacts it, so the endpoint a container healthcheck depends on keeps answering while an optional dependency is down. `lastProbeAt` and `lastProbeOk` are reported as null rather than false when nothing was measured, so "no storage configured" reads differently from "storage is broken".
- **A step-by-step operator guide for running the whole gauntlet on a remote machine**, in `README.md`. It covers what to install on a prepared server (Node 24, a full clone, the Playwright browser that no gate checks for, `actionlint`/`hadolint`/`oasdiff`/`diff-cover` at the versions the release workflow pins, Docker, the optional CodeQL bundle), the disk and `TMPDIR` budget a full pass actually needs, how to start a detached run that survives a lost connection and how to check on it from anywhere, how to tell a finished run from a killed one, how to read `summary.json` and the per-gate transcripts, why the first `verify:full` fails on `mutation` until its baseline block is recorded, how to re-run only the gates that failed, a troubleshooting playbook for the failure modes a remote box produces, and how to bring the results home by copy or by push.
- **A Documents page in the app**, listed in the sidebar only where the server says it has a document store, so nothing about the interface changes on a deployment without one. Drag a file onto the page or choose one, and it is encrypted in your browser and sent part by part, with the part it is on, the bytes sent and a cancel button visible throughout; a transfer that stops part-way can be resumed and re-sends only the parts the server does not already hold. Two checks run on the file before a byte of it is read: the server's size limit, and the file types the operator asked for — the second one can only ever be applied by the browser, because the server receives ciphertext and never learns a filename, and the page says so rather than implying the rule is enforced anywhere else. The list follows the vault list's conventions, virtualising above fifty rows with the position of every row announced, and a document whose details cannot be decrypted is listed plainly instead of being hidden. Alongside it: how much of the storage allowance is used, with a note that a document in the trash still occupies it; a notice that documents are deliberately not kept in the offline cache; and a load failure reported on the list itself with a retry, rather than as an empty account. Closing the tab during a transfer now asks for confirmation, and the page states plainly, before anything is chosen, that locking the vault cancels an upload — uploading is not activity, so the auto-lock countdown keeps running — with an extra warning when the file is large enough that the transfer is likely to outlast the deadline the vault will actually lock at — naming whichever of the two auto-lock settings governs it, and both when both will fire.
- **Opening one document in the app**, at `/documents/<id>`. It shows what the document is — the name, the type, the size, the tags, the note and the SHA-256 the file was sealed with, so a downloaded copy can be checked outside H-Vault entirely — and lets you rename it, retag it, edit its note, favorite it, move it between folders, send it to the trash, restore it or destroy it. Editing the details re-seals only the small encrypted block that holds them, under the document's own key: the stored file is never touched, never re-uploaded, and never leaves its original encryption. A document in the trash says plainly that it still occupies storage until it is deleted for good, and deleting it for good says that the only copy of the key that decrypts it is destroyed at the same moment.
- **Downloading a document, with the file checked on the way out.** The browser asks for the document, refuses to continue if the server answered with a different one, and refuses again if the sizes and segment counts the server keeps in the clear disagree with the copy sealed inside the document itself — naming exactly which of them disagree. Every segment is then authenticated as it arrives, in order, and a running SHA-256 of the whole file is compared with the one sealed at upload. Where the browser has a save dialog the file is written to disk as it is decrypted, so a large document never has to fit in memory; where it does not, it is assembled and saved the way every other download in H-Vault is. If the final checksum does not match, the file that was being written is emptied and you are told the download was discarded rather than being handed something that is not your document; if the transfer merely fails part-way, the file you picked is left exactly as it was, so choosing to overwrite an existing file and then losing the connection cannot cost you the old one. Filenames are cleaned before they reach the save dialog: path separators, control characters and the bidirectional overrides that make `report<override>gnp.exe` display as `reportexe.png` are all replaced with an underscore, so a disguised name arrives visibly changed instead of silently convincing. Locking the vault or leaving the page stops a download in progress instead of finishing it in the background.
- **The Settings rotation now enumerates and re-keys your documents**, which is what puts the rotation leg the API gained to use. It lists every document the account holds, in the trash as well as out of it, re-wraps each one's key under the new vault key and sends them in the same single request as the vault items and folders. No file is read, re-uploaded or even touched — only the 32-byte key that opens it moves — so rotating an account holding gigabytes costs the same as rotating an empty one. A document whose key will not open aborts the whole rotation before anything is sent, exactly as a vault item that will not re-encrypt already did, because committing the rest would leave that file sealed under a key the account no longer stores. On a deployment that has never had a document store configured, nothing about rotation changes; on one whose storage was configured and then removed, rotation is refused until it is restored, because a document key that cannot be read cannot be re-wrapped by anyone — and the refusal now says so.
- **An isolated document for displaying files, built and served but not yet shown.** H-Vault will never render a stored file in the page that holds your unlocked vault: an arbitrary file is arbitrary input, and the page that would parse it is the page holding the key. This release adds the container that solves that — a separate, minimal document served at `/sandbox.html`, embedded in a frame with no access to the application at all. It has no origin of its own, so it cannot read the application's storage, cookies, page or memory; it carries its own security policy, far stricter than the application's, which forbids it every kind of network request, background worker and plugin; and it receives the file's bytes over a private channel that is established exactly once and cannot be re-established. The application sends it four things and nothing else — the bytes, which renderer to use, the file's extension and the current theme — and never the file's name, the document's identity, any key or any token. A link clicked inside it opens nothing until the application has checked the destination and asked you. If it fails to start for any reason, the file falls back to a download rather than to an empty rectangle. Every renderer H-Vault has runs inside it, and nothing that parses a stored file runs anywhere else.
- **Documents are now shown in the app, inside the isolated frame rather than in the page.** Open a stored `README.md` and read it rendered the way GitHub renders one — headings, tables, task lists, strikethrough, autolinks, footnotes and fenced code with syntax highlighting — because it is sanitised with the same rules GitHub sanitises with, so looking right and being safe are one setting rather than two in tension. A stored web page renders through that same sanitiser, with a standing note that its scripts, styles and remote content are switched off. Text, source code and configuration files display with line numbers and, where H-Vault carries a grammar for the language, colour; a CSV or TSV becomes a table with its raw text one click away, and a JSON or JSONL document is pretty-printed with its original one click away. Images, including SVG, display through an ordinary image element that renders a picture and cannot run one. Audio and video play with controls and never start on their own. A file's encoding is read from its byte-order mark where it declares one, and a file that mostly fails to decode says so instead of showing a screen of replacement characters with no explanation. A very long file shows its first fifty thousand lines with a note giving the real size.
- **A file whose contents disagree with its name is refused, and the refusal says what it actually is.** A PDF renamed `.md` is not handed to the markdown reader; a file named `.png` that is not a PNG is not handed to the image renderer. The check runs one way only and never the other: most of what H-Vault displays — every text, source and configuration file — has no signature at all, so the absence of one is never a reason to refuse anything.
- **The Documents page decides whether it can show a file before it downloads it.** The type, the size and whether the document opens at all are read from the small encrypted block that travels with it, so a file too large to preview, or of a type H-Vault does not display, is never fetched and decrypted only to be turned away. PDFs are download-only, deliberately and permanently, and the page says why rather than showing a broken viewer: a PDF reader is a large third-party parser, and the best-known one has a documented history of running a document's own code in the page that hosts it. Anything H-Vault will not display keeps its download button and gains the reason it is not being shown.
- **A link inside a document asks before it opens.** Nothing in a displayed file can navigate anywhere by itself. Following a link shows a confirmation with the destination's origin on its own line — the part that says where you are actually going — and only ever for `http`, `https` and `mailto`; every other kind of address opens nothing and says nothing. A link to a heading or a footnote in the same document simply scrolls there. The document's name and its download button are drawn outside the frame, where nothing in the file can imitate them.
- **A document that cannot be opened with your vault key is shown as such**, with an alert explaining that its name, type, tags and contents are all sealed under a key that would not unwrap. It can still be moved between folders, favorited, trashed and deleted, which is what you need in order to get rid of it, and the controls that could not work — editing its details, and downloading it — are unavailable rather than offered and broken. Editing stays reachable by keyboard so the explanation can be read; it simply does nothing.
- **Two optional in-browser transforms on the upload panel: format a document, and repair its syntax.** Tick either before uploading a `.json`, `.jsonc`, `.json5`, `.jsonl`, `.ndjson`, `.md`, `.markdown`, `.yaml` or `.yml` file and H-Vault rewrites it before it is encrypted — indentation and spacing normalised by Prettier, and comments, single quotes, unquoted keys, trailing commas, an unterminated string or a truncated array turned back into strict JSON by a repairer. Repair covers the JSON family only, and elsewhere the box is unavailable with the reason shown: guessing at YAML indentation would change what a file means, and Markdown has no syntax error to repair. Both are unavailable past 5 MiB, and the reason for that is shown too. Formatting alone already accepts a trailing comma, and the panel says so rather than implying repair is the only thing that can fix a file.

The upload button is gone until you answer, and the answer is either the rewritten file or your original bytes unchanged. Every one of those numbers is worked out by H-Vault from its own copy of your file rather than taken from the component that did the rewriting.
- **A file that cannot be repaired stops the upload and says where.** The message, the line, the column and the offending line itself are shown, and the only way on is to upload the original unchanged — a half-repaired document is never produced. A file that is not plain UTF-8 is refused the same way and named precisely: a byte-order mark, UTF-16, or bytes that are not text at all. Each records what happened inside the document's own encrypted details: which transforms ran, the tool, its version, and a digest of the file as it was beforehand.

It also states that a file-level copy of a running storage engine is not a backup, and what a restore of one half without the other actually looks like.

It runs on every push rather than only before a release, because its headline case is that the engine itself accepts an undersized non-final upload part without complaint, which would shift every later segment boundary and leave a document permanently unreadable: the server's refusal of that part is the only thing standing in the way, and it is now checked against the real thing. The gate needs the `docker` CLI and reports itself as unable to run, never as passing, when the daemon is absent.
- **The release-tier gates now cover the document store's volume and its crash recovery.** `npm run test:resource` gained two scenarios: a document at exactly the operator's configured maximum size delivered part by part through the real upload route, which bounds what one transfer costs the server in time and memory; and a full account at the per-user document limit walked page by page, which proves the list is paged by the database rather than assembled in the server — the measurement that separates the two is recorded, along with the numbers the same test produces when it is not. `npm run test:recovery` gained three drills that kill a real server process with an uncatchable signal at the three points where the document store's own recovery code sits in a `catch` or a `finally` that a crash never runs: mid upload, between writing a file and recording it, and between deleting a file and deleting its entry. Each one then runs the hourly clean-up and checks that it reclaims exactly what the crash stranded and never a live document's file, which is the one mistake in H-Vault that cannot be undone from a backup.
- **The deployment clean room now carries a document and the isolated render document through the single published port.** `npm run test:deploy` uploads a sealed file, downloads it and compares it byte for byte, checks the storage footprint the deployment reports about it, and then deletes it — first into the trash, then permanently, which only reports success if the storage engine accepted the file's deletion, leaving the quota back at zero and the entry gone from the trash. It also proves the file and its key outlive a restart of the whole stack and a redeploy of the storage service on its own, and that the storage service publishes no host port at all. Two things about the document viewer are now checked where they are actually true: `/sandbox.html` comes back from the application with its own far stricter policy rather than off the web server's disk or as the app shell, and the viewer's script AND its stylesheet carry the two headers an isolated frame needs to load them while the application's own bundle still carries neither. Nothing else in the pipeline runs the real web server, so nothing else could see any of it. Finally, the storage credential trap is asserted rather than described: changing the secret alone makes the storage service refuse to start, and changing the key and the secret together starts it and still reads files written under the superseded credential.
- **The document store is now documented for the people who use it, not only for the people who run it.** `README.md` gains a Documents section covering what is sealed in the browser and what the server can still see, the two optional in-browser transforms, and a table of exactly which file types are displayed in the app and which are download-only — each of the download-only cases with its reason, so PDFs, Office formats and files with no extension such as `Dockerfile` or `.bashrc` read as decisions rather than gaps. It also states plainly that `DOCUMENT_ALLOWED_EXTENSIONS` restricts nothing on the server, which cannot see a filename, so any file type uploads and the setting is a browser-side convenience; and it repeats the backup boundary in user-facing terms, because a reader who meets it only in the operator guide meets it too late. A key-hierarchy diagram for per-document encryption sits alongside the existing ones.
- **`SECURITY.md` states the document store's threat-model delta.** What a compromised server learns about a document — the count, the size, the timestamps, the folder and the trash state, but no name, type, tag, note or content — with the size leak named as accepted rather than mitigated, and the note that the public `GET /api/v1/config` publishes the size cap, the quota, the document ceiling and the extension allowlist to anonymous callers exactly as the File Encryption cap already was. A new section describes the isolated frame every stored file is displayed in and lists all four of its residual risks, including the one that surprises people: a compromised renderer can carry the single file it was handed out by navigating itself away.

### Changed

- **Breaking for Docker deployments: upgrading now requires four new values in `.env`.** `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` and `S3_RPC_SECRET` are guarded the same way the database passwords are, so `docker compose up` stops before any container is created and names the variable that is missing. They ship empty rather than as placeholders, because a placeholder is a working credential. `S3_ENDPOINT` is not among them: the stack points the app at its own storage container. A PM2 deployment is unaffected and has no storage engine, so its document store stays off unless it is configured against storage of its own.
- **The application waits for storage to start, never for it to be healthy.** Documents are an optional feature, so a storage problem degrades documents alone rather than holding the vault's own startup down.
- **The local pipeline's two browser gates, and the flake gate behind them, now declare Docker.** Their harness starts the pinned object-storage engine in a container before it boots the dev server, because with no storage the document store is switched off and its journeys and four of its scanned views would fail for a reason that is not about them. On a machine with no daemon all three now report "could not run" rather than failing, exactly as the container and deployment gates already did.
- **The application's initial download is smaller.** `@hvault/shared` is now declared free of side effects, which lets the bundler drop the parts of it a given page does not use; the validation library it carries no longer travels into pages that never call it. The isolated render document benefits most — it now carries none of it at all, which is what its design always intended.
- **The operator guide for running the whole pipeline on a spare machine is now measured rather than estimated.** Every duration in it comes from measurement rather than estimate, most of it from one recorded release-tier run and the rest from two standalone fast-tier runs and the previous push-tier run: the fast tier is 1m 49s to 2m 23s and no longer fits its 90-second design budget, the push tier is 22 to 24 minutes across two clean runs, `flake` is 84 minutes, and the per-gate table is refreshed throughout. It also documents what was missing: how to check that the four pinned external binaries on the machine really are the pinned versions, the ~1.7 GB of container images a first run pulls, the fact that the object-storage harness leaves no volume to reclaim and needs no host port freed, that only a gate's declared reports are cleared before it runs so a stale side-artifact is not progress, that editing any tracked file mid-run makes the final ratchet reject every report written before the edit, and that the gate-can-still-fail sweep cannot pass until a first mutation floor has been recorded.

### Fixed

- **The two gates that check how the isolated document is served can no longer pass on a response that is not the file they asked for.** Both fetch the viewer's script, its stylesheet and the application's own bundle and then assert what each one carries, and a path with no file behind it can answer in two different ways: a 404, which carries none of those headers and so reads as a clean pass, or — where the server falls through to the single-page application instead — a 200 carrying the application shell and the application's own headers, which is exactly what the check for the application's bundle expects. The deployment drill already caught the first; neither gate caught the second, so a build that stopped emitting the bundle could be recorded as correct. Both now assert that each probe was answered by the asset itself, through one shared check that covers both shapes rather than two that could disagree.
- **Corrected an overstatement about what the document viewer's isolation buys.** These release notes, the viewer's own source and several places in the pipeline that describe it said the isolated frame could open no network connection at all. Its policy blocks every way of READING a response and names no external host, so nothing it runs can reach a third party or read an answer back — but it can still cause a request to this server, and the security documentation had already been corrected to say so. Every place that describes it now states the same bound.
- **The flake gate's own report no longer contradicts itself when it finds a flake.** Its summary sentence recited a zero-failure statistical bound regardless of the count it had just reported, so a run that found one failing order published `1 failing run(s) ... With 0 failures this bounds ...`. A sample that produced a failure has measured a flake rather than bounded one, and the report now says which of the two it is holding.
- **The browser gates no longer leave a container and a RAM-backed database directory behind on every run.** `npm run test:e2e` and `npm run test:a11y` start a real object-storage container and an in-memory MongoDB, and the harness that owns both was being killed outright rather than asked to stop, so each green run stranded them: eight storage containers and a directory per run had accumulated on the machine that runs the pipeline. The harness is now signalled and given time to finish, it is the process the runner actually launches rather than sitting behind two wrappers, and a second request to stop it waits for the first instead of returning while the removal is still in flight. It prints a line when the teardown starts and another when it has finished, so a run that was interrupted can be told from one that cleaned up.
- **A task list inside a document preview is now readable with a screen reader.** GFM renders a checked or unchecked task as a disabled checkbox with the task's text beside it, so nothing named the control and a screen reader announced only "checkbox, checked" without saying what was checked; the same applied to any form field the sanitizer had neutralised into a checkbox. Each one now carries the text of its own list item as its accessible name, bounded so a paragraph-length task cannot become a paragraph-length announcement, and the checked and disabled state a reader needs after the name is untouched.
- **The isolated document a preview renders inside is now a named landmark**, so a keyboard or screen-reader user can move into the preview and out of it, and can tell it apart from the surrounding page's own main region.
- **An account that holds a few documents more than the advertised limit can rotate its vault key again, and can see those documents at all.** The document count is checked when a transfer is opened and not again, so three concurrent uploads can pass the same reading and all commit: an account can finish a little past the limit. Both the rotation payload's cap and the page ceiling the browser walks its own document list with were derived from the advertised limit instead, so such an account had its rotation refused in both directions at once and, worse, simply never saw the extra documents in the list or the trash — they could not be opened, downloaded or deleted while their bytes kept counting against the quota. Both now derive from the real ceiling.
- **A document preview no longer hangs for ever on a file whose extension happens to name a JavaScript property.** A name like `notes.constructor` resolved through the lookup table's prototype instead of falling back to "no preview", and the viewer then sat on a loading spinner with no download offered. The lookup tables carry no prototype at all now, so every such name is simply unpreviewable, as it always should have been.
- **Locking or signing out while an upload is being committed no longer leaves the finished document's name and note in memory.** The teardown could not reach a transfer in the moment between its commit and its metadata being opened for the list, so a lock landing there put a decrypted name, type, note and checksum back into a store that had just been emptied, where it survived until the next refresh and, after a sign-out, into the next account signed in on that tab.
- **A vault list page no longer depends on chance when many items share a timestamp.** Listing items and listing the trash now order by identifier within a tie, so an import or a bulk action that stamps one instant across many rows cannot make a paged walk return one row twice and another not at all.
- **Deleting a folder now takes its documents with it.** `action=delete` moves the folder's documents to the trash and `action=move` re-parents them to the folder's parent, exactly as it has always treated the folder's vault items; the post-delete sweep that clears a stale folder reference covers them too. Previously a folder's documents kept pointing at a folder that no longer existed.
- **Documents left in the trash are now purged on schedule.** The nightly clean-up removes documents trashed more than thirty days ago together with their stored files, the same way it has always removed expired vault items. A file the storage service will not delete leaves its entry marked for the next run rather than removing an entry whose file is still there.
- **A failed vault-key rotation now says why.** The Settings flow reported every failure as a flat "Failed to rotate vault key", including the refusal that names exactly which of items, folders or documents the request fell short on and what to do about it. A refusal the server wrote for the user is now shown to the user; a server fault still reads as a generic failure, because its body is deliberately redacted to its status text.
- **A vault-key rotation no longer strands a row created while it was being prepared.** The browser lists the account, re-encrypts what it listed and posts the result, but the write fence that blocks other sessions only goes up when that request arrives — so an item, folder or document created in between was left sealed under the old key while the key itself was replaced, silently and behind a success response, leaving it permanently unreadable. The server now checks, as part of the write, that the request names every row the account holds, and refuses with a conflict telling the client to re-read the vault and retry. The check counts distinct ids rather than list length, because a client that double-read a page while another session was writing would otherwise send the right number of entries with one of them repeated and one row missing; a request naming the same row twice is now rejected outright. Trashed rows are counted, since they are sealed under the same key, and a document whose permanent deletion has not finished is counted until the hourly cleanup completes it — the refusal says so.
- **A finished document upload is no longer thrown away when the server dies mid-completion.** Assembling the stored object and deleting the transfer's staging row are two steps, and the storage engine invalidates the transfer's handle on the first of them; a crash between the two therefore left a correctly assembled file that the retry reported as missing, so the client uploaded the whole thing again and the assembled copy became storage nobody could reach. The retry now recognises that state — it confirms the stored object is exactly the length the transfer's own part ledger accounts for — and commits the document instead of asking for the file a second time.
- **A transfer whose storage-side upload has already gone can be cancelled again.** Cancelling asks the storage engine to abandon the upload first and deletes the row second. When the engine had already abandoned it — a bucket lifecycle rule, or an earlier cancellation whose response was lost — it answered "no such upload" and the cancellation failed, leaving a row that held one of the account's concurrent-transfer slots and part of its storage quota until it expired, up to a week later. That answer is now treated as success, because it describes exactly the state the request was asking for; every other storage failure still refuses, since the engine may still be holding the parts the row names.
- **The per-document size limit is now measured on the bytes that actually arrived.** It was checked only against the size a client declared when it opened a transfer, and a client is not held to that number: only a non-final segment must be full, so a transfer that declared one megabyte could legally deliver a full eight-megabyte final segment. Against a small operator limit that stored a document several times larger than the limit the same account is told about. The limit is re-checked at the moment of commit, and a transfer over it is refused and released rather than left to occupy the account's quota until it expires.
- **A transfer waiting to be cancelled can no longer be pushed off the transfers list.** The list is newest-first and deliberately includes transfers that have expired, because an expired one is what a user needs to find in order to cancel it — but it was capped at exactly the number of transfers that may run at once, so with a full set running the expired row was the one dropped. Its cap is now twice that, which is the real ceiling.
- Staging-transfer responses no longer carry Mongoose's internal version key, matching the projection every committed-document response already used.
- **A single over-long entry in `DOCUMENT_ALLOWED_EXTENSIONS` no longer changes the File Encryption tool's size limit.** The advisory extension list is published by `GET /config`, and an entry longer than an extension can be made the whole response unreadable to the browser, which then fell back to the built-in default for a completely unrelated feature. Over-long entries are now dropped at startup with a warning naming them, and the browser reads the File Encryption limit without validating a block it does not use, so a mistake in one feature's configuration stays in that feature.

### Security

- **`browserslist` updated to 4.28.8 in the dependency tree**, clearing two advisories (a prototype-pollution denial of service and unbounded memory growth from distinct query results) that the container scan reports as fixable HIGH against the bootstrap image. It is a build-time transitive dependency and no runtime behaviour changes.
- **Three transitive dependencies moved to their patched releases**, taking the production dependency tree back to zero advisories at moderate or above. `qs` 6.16.0 is the one that reaches a running server: it is the query-string parser Express and its body parser use, and the two advisories it clears are an array-limit bypass through comma-separated bracket keys and a denial of service through an attacker-controlled value. The other two are build-time only — `fast-uri` 3.1.7 (four advisories covering host confusion and server-side request forgery in URI normalisation) and `postcss` 8.5.26 (an arbitrary source-map read when no `from` is given). Neither `qs` nor `postcss` is declared by this project — both arrive as transitive dependencies — so the two version floors already pinned in the root `overrides` were raised to the patched releases so they cannot regress, exactly as the `brace-expansion` floor was. No runtime behaviour changes.
- **The Nginx image is rebuilt against the current Alpine package set**, taking `libexpat` to 2.8.4-r0 and clearing two HIGH advisories. The image already upgraded its packages at build time; what was stale was the cached build layer that did so, not the instruction.
- **Deleting an account now erases its documents and their stored files.** Account deletion removes every document entry and every unfinished transfer, then deletes the account's files from object storage. Because the entry holds the only wrapped copy of the key that decrypts a file, an entry that is gone leaves any remaining file permanently unreadable. Deletion still succeeds and is still reported as complete when the storage service is unreachable, with the failure logged for the operator; on a deployment with no document store configured the step does nothing at all.
- **The application may now embed one document, and only its own.** Its content-security policy previously forbade framing anything at all; it now permits exactly `'self'` — never a `blob:`, `data:` or wildcard source, either of which would let injected markup carry its own contents and run them under the application's own policy. The isolated render document is served with a policy of its own instead of inheriting one, and that policy is pinned whole, directive by directive, in two independent places: over the constant, and over the header the built artifact actually sends. Its script and stylesheet are served from their own directory, and that directory alone is readable by the frame's anonymous origin — the application's own bundle is not.
- **Nothing in a stored document can execute, and the rendered result is what is checked.** Markdown and HTML are sanitised with `rehype-sanitize`'s default rules — the ones modelled on GitHub's own — and the sanitised result is turned into page elements directly rather than back into text that is parsed a second time, which is the shape that lets a stripped script reappear. Scripts, event handlers, `javascript:` links, frames, embedded objects, forms, inline SVG and style attributes do not survive, and the identifier-shadowing trick that lets a document redefine parts of the page's own scripting is defended against by the same rules. A stylesheet or a page title inside a stored file is removed rather than unwrapped, so its text cannot arrive looking like the document's first paragraph. A committed corpus of hostile documents is asserted against the elements a browser actually ends up holding, not against what the sanitiser reported.
- **A displayed document cannot fetch anything.** Images referenced from somewhere else on the internet are not loaded, and the reader is told rather than left looking at a broken image: fetching one would tell whoever wrote the document that you opened your private copy. Images, audio and video are played from data the frame already has, never from a request.
- The wrapped per-document key (`encryptedDek`) is masked in request logs, alongside the vault key and the backup key, so no request body carrying it can leave a key in a log line.
- **Formatting and repair run inside the same isolated frame that displays a document, not in a background worker in the application itself.** A worker would share the application's origin, so a flaw in the formatter or the repairer could have used your session to talk to H-Vault's own API on your behalf. Inside the isolated frame the same flaw lands somewhere holding no key, no token, no cookie and no storage, that can reach no host but this server and read nothing back from it. The frame is created fresh for each file, is handed the text and the two settings and nothing else — no key, no name, no identifier — is bounded by a deadline so a file that never comes back cannot leave an upload waiting, and is destroyed afterwards.
- **A downloaded document can no longer be written into the browser's offline cache**, which is now checked against the service worker the build actually produces rather than against the instruction that asks for it. API responses were already excluded; a document's encrypted contents travel that way, and the cache outlives locking, signing out and closing the browser.
- Patch the application image's Alpine OS packages at build time, clearing a fixable HIGH OpenSSL advisory (`libcrypto3` / `libssl3`) that the upstream Node base image had not yet been rebuilt against. The Nginx image already did this; both runtime images now do.

### Added

- **The local pipeline now has three entry points instead of one.** `npm run verify:fast` runs the fast tier only — the Node floor, the secret scan, lint, the format check and the type check, about 80 seconds — which is short enough to run before every commit. `npm run ci` is unchanged and still runs everything the pre-push hook runs. `npm run verify:full` adds the release tier. Every gate declares which tier it belongs to, and `npm run ci -- --list` now shows it.
- **Every gate writes a machine-readable report to `.testfortress/reports/`.** The three test suites and the E2E run emit JUnit XML, coverage now includes Cobertura beside the existing lcov, ESLint emits SARIF, the secret scan emits JSON, and each gate's full transcript is saved beside them. `npm run report` collects the warning counts into `warnings.json`. The directory is regenerated on every run and is not committed.
- **`npm run ci -- --json` prints one JSON document describing the run** — per gate: its task name, status, duration, gate criterion, report path and a one-line summary — so a tool can read a run's result instead of scraping the terminal. The same document is always written to `.testfortress/reports/summary.json`. (`npm run` prints its own banner to stdout first; use `npm run --silent ci -- --json` to pipe it.)
- **`.testfortress/verify.json` lists every gate**: its canonical name, the command that runs it, its tier, what it must achieve, and the report it writes. The pipeline checks itself against that file on every run and refuses to run if the two disagree.
- **A gate now declares what it needs.** The container gate says it needs Docker and the type-check and test gates say they need a built `@hvault/shared`, so a missing prerequisite is reported as "cannot run", with the command that fixes it, instead of failing as though the code were broken.
- **The pipeline now checks that nothing has been done to the gates themselves.** `audit:integrity` reads every tracked and untracked file for the markers that weaken a check — a skipped or focused test, a silenced type checker or linter, an inline coverage pragma, a swallowed error, a retry that hides a race, a sleep used as synchronisation — and fails unless each one is either absent or recorded in the new `.testfortress/suppressions.json` with an owner, a reason, an expiry and the exact rule it excuses. Inside a file that defines a gate, a neutered exit code, a committed test filter, a strictness downgrade, a tautology or a hook bypass cannot be recorded at all; it has to be fixed. Documentation is exempt, so the project can keep describing the patterns it forbids.
- **`audit:ratchet` holds every gated number to its recorded high-water mark**, from the new `.testfortress/baseline.json`. Each field declares a direction: coverage percentages, absolute line counts, the measured file set and the test count may only rise, while warnings and suppressions may only fall. A number moves only through `ratchet-check.mjs --accept --reason "..."`, which moves each field in its improving direction alone and refuses while anything is failing or unmeasured. Recording the denominator beside the percentage is what makes a coverage gate real: dropping a file from the measured set raises the percentage while covering less code, and that now fails.
- **`npm run verify:selftest` proves every registered gate can still fail.** It copies the tree to a temporary directory, plants one defect per gate — an explicit `any`, a false assertion, a broken Nginx directive, a dependency with a known advisory — and requires each gate to return non-zero for a reason its own report attributes to that defect. A gate registered without a defect-injection case is a hard error naming it. It runs in the release tier.
- **`npm run audit:integrity`, `npm run audit:ratchet` and `npm run audit:ratchet:full`** run those checks on their own. The first two join the fast tier and add under a second to it; the third runs with the push gate, after the suites it reads.
- **`npm run deadcode` finds code nothing reaches.** `knip` reports unused files, exports, exported types and dependencies, plus dependencies that are imported without being declared — the failure mode that survives every test and breaks on a clean install — and `jscpd` measures duplication against a ceiling committed in `.jscpd.json`. The ceiling is the project's measured duplication, and `.testfortress/baseline.json` records the same number as a limit that can only fall, so raising it to make room for a new clone fails the ratchet. Neither tool has an ignore list, by design: a finding is answered by deleting the code.
- **`npm run audit:config` lints the three configuration languages nothing else read.** `actionlint` checks the release workflow including its expressions, `hadolint` checks both Dockerfiles, and `spectral` checks the OpenAPI 3.0.3 document the server actually serves, generated from source at gate time rather than from a copy that can drift. The gate fails on error-level findings; everything below that is counted into the baseline, where it can be paid down and cannot grow.
- **`npm run audit:licenses` holds the production dependency tree to a committed allowlist** in the new `.licenses-allowlist.json`. Every package a self-hoster installs is checked against it, any copyleft licence fails outright regardless of the allowlist, and a package with no licence data is a violation rather than a gap. The current tree is 312 packages: MIT, ISC, Apache-2.0, BSD-2-Clause, BSD-3-Clause and MIT-0. The enumeration is itself cross-checked against the physical `node_modules` tree, so a walk that silently skipped a subtree fails the gate instead of passing it.
- **`npm run test:security` checks every endpoint for cross-user leakage, from a committed table of the whole route surface.** `packages/server/tests/support/routeTable.ts` classifies all 57 API routes — method, path, whether the path carries an id the caller must own, whether authentication and CSRF apply, and which rate limiters are mounted — and the suite reads the real Express router stack and fails if the two disagree in either direction. Adding an endpoint therefore fails the gate until it is classified, and classifying it as taking an owned id fails the gate again until it is actually exercised. Every such route is then driven through the real server against a real database with two accounts: the owner succeeds, a second user presenting the first user's id is refused, an unauthenticated caller is refused, a malformed id is rejected, and the target document is byte-identical afterwards, `updatedAt` included. A foreign id is also required to be indistinguishable from an id that does not exist, so the response cannot be used to enumerate other people's items. The limiter column is checked against the middleware actually mounted, which is the first automated check on that placement across the whole surface.
- **`npm run test:observability` checks what the server says about itself.** Three surfaces carry a request's secrets back out of the process once it has arrived — the log line describing the request, the audit row describing what was done, and the error body describing what went wrong — and a leak into any of them is durable, invisible to the client, and kept for a year. The gate drives the real masking configuration the server mounts (rather than a copy of it written into a test), plants a unique value in every sensitive field of a real sign-in, item creation, export and failed re-authentication, and requires that none of them reaches an audit row while the rows themselves still record what happened. It also pins the production error contract: a 5xx body is redacted to its status text with no stack, a 4xx still explains itself, and the same 5xx outside production still carries its detail — so the redaction is proven to be targeted rather than blanket silence.
- **`npm run test:property` generates its own inputs, in two timezones.** Six runs — the shared, server and client property suites, each once in UTC and again in a zone that observes daylight saving — assert the invariants that only hold for _every_ input rather than for a chosen one: anything encrypted comes back byte-identical, including half a megabyte of arbitrary unicode; every stored item re-parses under its own schema, so what the vault writes it can always read back; a secret's expiry date is returned untouched when neither control was edited, including during the repeated hour of a daylight-saving fall-back, where two different instants show the same wall-clock reading; the password-strength band and crack-time estimate never go backwards as a password gets stronger and never render "Infinity"; an identity's delivery notes never appear in a rendered address, a copied billing address, or the address search; and no sequence of folder create, move and delete operations can produce a loop or a chain deeper than the limit. The second timezone is not thoroughness for its own sake: the expiry branch is unreachable in UTC, so a suite that only ran there could not tell a correct implementation from a broken one. Each failure prints the seed that reproduces it, and every counterexample found this way is committed as a named test.
- **`npm run test:snapshot` pins the export formats byte for byte against verified goldens.** The Bitwarden JSON, Bitwarden CSV and Chrome/Edge CSV serializers write files another password manager reads, and until now nothing compared a whole document: a reordered column, a renamed key, a `null` that became `""` or a field that quietly stopped being emitted would all have shipped unnoticed, and a user would have discovered it at the moment they were migrating away. One item of each of the five types plus a folder is now exported to each format and compared with a committed golden, and each golden carries a note naming who verified it against the target application's documented import format, on what date, against which source, and — explicitly — what was not verified. The same gate closes the loop: re-importing what was exported yields the same logical items, checked with the real import parsers and the real identity rules, so exporting and re-importing an item still matches it rather than duplicating it.
- **`npm run test:fuzz` feeds the import parsers and the restore endpoint hostile files.** The seven import formats and the backup restore are the only places where a file somebody else wrote becomes vault data. Every parser is now driven with arbitrary bytes, with generated documents whose every field is hostile, and with a committed corpus of hand-minimized files — an empty file, a byte-order mark, mixed line endings, a million-column row, a fifty-thousand-row file, deeply nested JSON, lone surrogates, duplicate and prototype-named headers, and a value one character past every length limit — and must always either return items that pass their own validation or fail with a typed error naming the format. Restore is driven with adversarial backup documents — dangling parents, a folder that is its own parent, mutual and three-way cycles, ids belonging to another account, repeated ids and colliding search hashes — and must leave a folder tree with no loops, account for every row it was sent, and never lose a well-formed row to a duplicate key. Each leg runs under a wall-clock deadline, so a parser that hangs on a crafted file fails the gate instead of hanging the run. The gate sits in the release tier; its suites still run inside the ordinary test gates on every push.
- **`npm run test:smoke` starts the built artifact and completes a real vault journey against it.** Until now nothing anywhere ran the JavaScript this project emits: the build gate proves it compiles, the E2E suite drives the sources through the development server, and the container gate builds the images without ever starting one. The new gate stages the compiled server and the client bundle into a temporary directory laid out exactly as the production image, boots it in production mode against a real database, and registers an account, signs in, stores an item and reads it back — checking that the stored ciphertext comes back byte for byte and that a deep-linked page is served with the security header it is supposed to carry. It runs with the push gate and takes about five seconds. Production mode is most of the point: it is where a `dev-` secret or a non-HTTPS origin is refused, where the rate limiters stop being no-ops, and where a 5xx body is redacted — none of which any other gate exercised.
- **`npm run test:deploy` stands the whole Docker stack up from nothing and drives it through its single published port.** The deployment clean room destroys its own containers and volumes, builds and starts the five services, and requires every one of them to reach its expected state — including both one-shots, whose silent failure would cost the deployment its indexes and its least-privilege database user. It then checks that the stack publishes exactly one host port and that the port is bound to loopback, that nothing answers on the database port, that a full register–sign-in–store–read journey works end to end **through Nginx** rather than against the API directly, that the data is still there after a restart, that re-running the index bootstrap on an initialised database is a no-op, and that a database password rotated by an operator survives a redeploy instead of being overwritten. It uses its own project name, port and subnets, so it can be run on a host that is already serving H-Vault. It sits in the release tier, because it builds four images and restarts five containers.
- **`npm run test:a11y` checks that the application can be used without a mouse, and without seeing it.** Two things nothing checked before. First, axe runs over fifteen views and modals in the real signed-in application — the sign-in and registration pages, the vault list, an item, the create dialog on each of its five item types (including the billing-address section expanded and the saved-address picker open), settings, vault health, the file-encryption tool and the unlock screen — and any serious or critical finding fails the gate. Second, the keyboard behaviours a scanner cannot see are pinned in a real browser: the saved-address picker keeps typing focus in its search field while announcing the highlighted address, Escape closes that panel without discarding the half-filled item behind it, focus lands somewhere useful every time the billing-address section appears or disappears, and the create dialog holds the focus ring instead of letting Tab wander onto the page underneath. Automated scanning finds roughly a third of real accessibility defects, so this is a floor rather than a conformance claim; the moderate and minor findings are recorded in the report rather than ignored.
- **`npm run ci:local` verifies the current commit from a checkout that has never met your machine.** It creates a temporary worktree at `HEAD`, installs strictly from the lockfile, and runs the full gauntlet there — so a dependency tree carried over from another platform, a stale tool cache, or a file mode inherited from the checkout cannot make a broken commit look green. Uncommitted work is deliberately not included, and the run says so; the temporary worktree is removed even when the run fails.
- **`npm run test:resource` asks what a full vault costs.** Every other suite works with a handful of items, so nothing measured what happens at the ten-thousand-item limit the product advertises. Seven scenarios now do, against a real database: a vault four times the backup size limit is refused before most of it has been read (the collector streams by design, and a rewrite that reads it all first returns exactly the same refusal, which is why this needed measuring rather than asserting); the largest backup the configuration permits is still produced in full; ten thousand items are re-encrypted in one key rotation, and a rotation naming one item that does not exist changes nothing at all — not one row, and not the stored vault key; a 25 MiB backup whose request body is inflated past 26 MB by JSON escaping is still accepted and restored row for row, with the two refusals on the other side of that boundary kept distinguishable; and both scheduled cleanup sweeps are shown to use their indexes rather than reading every row of the largest collection every six hours. Each budget is set from a measured spread over repeated runs, and the report records both the numbers and how much variation they were set against. It sits in the release tier, because it takes about a minute and its measurements are only meaningful in a process running nothing else.
- **`npm run audit:bundle` holds the browser bundle to a committed size budget.** zxcvbn, Argon2id and the file-encryption tool are all loaded on demand on purpose, and turning any of them into an ordinary import is a one-line change that type-checks, lints, passes every test and builds cleanly — while making the application slower to start for every visitor. The build already declared an 850 kB chunk limit and only ever printed a warning about it; that limit is now enforced, together with a ceiling on every other chunk and on the initial payload a first-time visitor downloads before anything renders. It runs with the push gate and takes milliseconds.
- **`npm run test:upgrade` checks that an upgrade can still read what the previous release wrote.** Eight releases of encrypted data have shipped and nothing has ever verified this, which matters more here than in most applications: the server holds only ciphertext, so a field that quietly becomes required does not degrade a feature, it turns a working item into one that says it cannot be decoded — with the password inside it. A vault generated at the 0.7.0 tag, by that release's own encryption and validated by its own rules, is now opened by the encryption this release ships, re-validated and read back through the current code: every item must decrypt to the same bytes and parse to exactly what 0.7.0 parsed it to, so neither a dropped field nor a newly injected default can pass unnoticed; no item type may declare a required field, so documents older than the fixture are covered too; an item from before recovery codes, delivery notes or two-line street addresses existed must still open; a folder with no restore marker and a session with no hard deadline must still be accepted, and that session must still slide by seven days rather than silently gaining an expiry nobody chose; and the two settings added since must be filled in on read, because nothing backfills them. The same gate loads the current server's configuration from the file 0.7.0 shipped: it must load in production, the four variables since removed must be ignored rather than fatal, and each required secret that is missing or blank must refuse the boot by name and immediately — the alternative being a password manager running on a signing key published in this repository. Both fixtures carry a note recording who generated them, when, from which tag, and what was not verified; neither is ever regenerated from the current code. It sits in the release tier; its suites still run inside the ordinary test gates on every push.
- **`npm run test:recovery` rehearses the two days this application is built for: the one where the backup is all that is left, and the one where the server dies mid-write.** A backup was only ever restored back into the database it came from, which cannot tell "the row was restored" from "the row was already there", and every row in those tests carried placeholder text rather than real ciphertext — so nothing had ever shown that a backup file opens somewhere else. It now does, on a second database on a second server: a vault is built through the real API with real encryption, downloaded and signed the way the browser signs it, and restored into a brand-new account that has never seen it, where every item must decrypt to the same bytes and stay attached to its own name — emoji, right-to-left text, embedded quotes and line endings included — the folder must come back with its item still filed in it, and the account's own key must be untouched, because a restore re-encrypts what it is given and never adopts the key from the file. The document the server emits is also shown to survive the round trip that signature is computed over — the property every signed backup silently depends on, since a document that no longer re-serialises identically would fail verification on the day it is needed — and a file is worthless without its backup password. The second half kills a real server process with an uncatchable signal at five points around the two operations that claim to be all-or-nothing. A key rotation interrupted between raising its write fence and storing the new key must leave the stored key untouched so the vault is still the user's to open, must leave the fence up so a second device cannot write something the rotation would strand, and must record the key it was moving to so the interrupted rotation can simply be run again — which it is, and it completes; the next sign-in must then clear that fence only once the dead rotation's lock has genuinely expired, and never while another server might still be rotating. An import killed before its write, inside its transaction, or after it committed must never leave part of itself behind, and the lock the dead process was holding must free the account again rather than wedging it. It sits in the release tier; its suites still run inside the ordinary test gates on every push.
- **`npm run test:mutation` asks whether the tests assert anything at all.** Coverage says a line ran; nothing said it was checked. Every production file in the three packages is now changed on purpose, one edit at a time — a bound moved by one, a comparison flipped, a branch inverted, a message emptied, a whole block removed — and the suite has to notice. What it found on its first run is the point of having it: schema bounds that no test probed at their limit, format patterns whose anchors could be deleted without a single failure (a 64-character search hash with anything appended to it was still accepted), the rule that a folder's encrypted name, its IV and its tag must move together — which nothing asserted, so replacing that rule with "always allow" changed no test — and a backup-code parser whose entire diagnostic half, the part that tells a user which character it could not read and where, was unmeasured. Static code counts: every bound in this project is built when its module loads, so the option that skips such changes would have discarded 684 of 2,008 changes in the shared package alone, 461 of them inside the schemas. It sits in the release tier, because a full run is hours; after the first, it re-tests only what changed.

  **Its floor has not been recorded yet, and until it is this gate fails rather than passes.** The score, the number of changes it was measured over and the exact list of files are all meant to be recorded in `.testfortress/baseline.json`, each able to move only in the direction that means more code checked. No `mutation` block exists there today, and the gate treats that as a failure on purpose: a run that mutates the whole codebase for hours and then exits zero having compared its result against nothing is not a gate, so the bootstrap is loud instead of silent. The consequence is stated rather than hidden — **`npm run verify:full` does not pass today**, and the tier-1 surface that `npm run ci` and the release workflow run is unaffected and green. Two of the three legs have been measured (shared: 79.9% over 2,008 mutants, with its survivors triaged into the ledger as SUP-0028 and SUP-0029; client: 74.57% over 15,322), and both were measured on a machine that was not reliably idle, which inflates a score rather than lowering it — a test starved of CPU fails on a timeout and Stryker counts a timeout as a kill. Neither number is therefore recorded as a floor. See the ledger entry for what closes this.

- **`npm run coverage:check` requires the production lines a change touches to be covered.** A coverage percentage is an average over eleven thousand lines, so a module arriving with no tests at all moves it by hundredths — well inside the noise of ordinary work — and every existing threshold stays green while the code written today is the code nothing checks. That is not hypothetical: it was demonstrated while building this gate, by adding a wholly untested function to the shared package and watching the suite pass. The gate compares the change against the trunk and requires every production line it touched to be covered. It also closes the hole that measurement has on its own — a file in no coverage report is indistinguishable from a file that does not exist, so an untested new module would otherwise read as full coverage over nothing — by checking every changed production file against the set the suites actually instrumented. Each package is additionally held to the line, branch and function coverage already recorded for it, which can only rise. The one way to ship an uncovered line is a dated, owned, expiring entry in the suppression ledger naming that file and bounding how many lines it excuses; when the entry lapses the gate goes red on its own. It runs with the push gate and needs `diff-cover` on the path — an absent one is reported as "cannot run", never as a pass.
- **`npm run test:flake` asks whether this suite gives the same answer twice.** Every gate in this project assumes the test suite's verdict is a property of the code; nothing had ever checked it. The suites shuffle their order on every run, but from one pinned seed — so every push has been taking the same shuffled order, and an order-dependent failure would have surfaced not on the change that caused it but on some unrelated change months later, on somebody else's machine. The new gate runs all three package suites ten times, each in a different order derived from that same seed so the whole sequence is still reproducible, with the file parallelism the push tier uses and with the generated inputs held still so a red run means an ordering problem rather than an input nobody had drawn before; then it runs the whole browser suite three times over with retries pinned off. A failing run is named — the test, the package and the order seed that produced it — because "run 7 failed" is not something anyone can act on. What it reports is a rate rather than a property, and it says so in its own report: ten clean runs bound the per-run flake rate near one in ten, they do not establish zero, and no finite number of runs can. Both numbers are held to their recorded value in opposite directions, so the sample can never quietly shrink and an observed flake can never quietly be accepted. A flake found here is a bug report about the code or the harness: it is fixed at its cause, or quarantined for thirty days in its own tier with its own report, and never retried away. It sits in the release tier, because it takes about an hour.
- **`npm run test:dst` runs the whole suite again in a timezone that changes twice a year.** Everything this application shows about time is computed in local time by design — a secret's expiry countdown, the two controls that edit it, the vault-health "last checked" label — and every gate ran in UTC, where local time and UTC are the same thing, so an assertion that was right only by that coincidence was indistinguishable from one that was right. The property suites already ran in a daylight-saving zone, but only they did: 7,433 tests had never been executed anywhere else. They have now, and the application code came through clean. The gate narrows nothing — it is the same suite the push tier runs, in the other zone — so a test that passes in UTC and fails here is reporting an undeclared dependency on the machine's clock. It sits in the release tier and takes about four minutes.
- **`LOG_DIRECTORY` chooses where the rotating log files are written.** Unset, they land in `logs/` beside whatever directory the process was started from, which is what happened before; set it to put them on a mounted volume instead. A blank value is treated as unset.
- **`npm run audit:secrets:full` scans the whole tree and the full git history.** A credential that reached history is already compromised — it is in every clone and every fork, and no later commit takes it back — so the gate names the commits that carry it and asks for rotation rather than deletion.
- **`npm run audit:openapi` refuses to let the HTTP contract break without a MAJOR version bump.** The OpenAPI document the server serves is now compared against a committed snapshot of the release it last described, `packages/server/openapi.snapshot.json`, and any change that would break an existing client — a removed endpoint, a removed response field, a newly required parameter — fails the gate unless that release is itself the major bump — one MAJOR above the snapshot, and the `.0.0` of that line. The narrower rule is the point: "any higher MAJOR" would have been permanently satisfied from the first bump that left the snapshot behind, so every later release in the line could have carried unversioned breaking changes while the gate still reported that it checked. The distinction this draws is one nothing else here could: removing a field from a response breaks no type, fails no test and builds cleanly, while a client that stops receiving it simply stops working. The snapshot moves only alongside the version it names, and its size is recorded in the baseline where it can only grow — an addition is never a breaking change, so a snapshot that shrank would let the gate compare the whole contract against almost nothing and report success. It runs with the push gate and takes about two seconds; it needs `oasdiff` on the path, and an absent one is reported as "cannot run" rather than as a pass.

### Changed

- **The record of what this project does NOT test is now written down where the gates can see it.** The testing audit adjudicated twelve kinds of testing as deliberately deferred and one — cross-browser end-to-end — as applicable and missing, and said each carried a dated ledger entry naming an owner and a review date. None of them did: the ledger held only the entries covering markers in the source. All thirteen now exist in `.testfortress/suppressions.json`, alongside a fourteenth for the accessibility scan's light-theme-only scope and the dark-theme contrast defect that scope hides, each with the reasoning that was used to defer it and a date on which it has to be argued again. They are exempt from the ledger's entry ceiling, which is what makes recording them possible at all — the ceiling ratchets downward, so a debt with no marker in the tree could otherwise only be written down by loosening the very limit it sits under. `.testfortress/verify.json` shipped an empty `gaps` list beside all of this; it now summarises the same eight areas and points at the ledger entries rather than restating them, so the two records cannot disagree.
- **A release is now published only after the full pipeline has passed on a clean checkout, and only when the version says so.** The release workflow used to be gated on nothing, on the argument that a commit reaching `main` had already been checked by the pre-push hook — an argument the project's own documented escape hatches defeat, since any of the three puts an unverified commit on `main` and the release published it with nothing having run anywhere. The workflow now runs `npm run ci` — the same gates the hook runs, no narrower set — and creates the tag only if it passes. This costs nothing: the repository is public, where hosted runners are free and uncapped.
- **The release tag now follows the version in `package.json` instead of walking ahead of it.** Every push to `main` used to mint the next patch tag on its own, so a release could be published as `v0.8.1` while the artifact inside it — `/health`, the OpenAPI document — reported `0.8.0`, and no release notes had been written for it. The version in `package.json` is now the only thing that decides: a push whose version is already tagged publishes nothing and says so, a push that bumps it is released under exactly that tag, and a tag series that has somehow run ahead of the version stops the workflow rather than guessing. **Cutting a release is therefore a deliberate act: bump the version and write its changelog section, as the release ritual already described.**
- **GitHub Releases now carry the curated `CHANGELOG.md` section instead of a generated list of commit subjects.** This project treats a changelog entry as a blocking requirement of every change, and the release then discarded it at the one place users actually read release notes. The matching `## [X.Y.Z]` section is published verbatim, and a release whose section is missing or empty fails rather than shipping with nothing to show.
- **The pipeline now runs every gate and reports all the failures, instead of stopping at the first one.** A run that would previously have told you about one broken gate at a time now tells you about all of them at once. `npm run ci -- --bail` restores the old stop-at-the-first-failure behaviour; `--continue`, which used to request the new behaviour, is now accepted and ignored, since it asks for what already happens.
- **A failed build no longer drags the gates that depend on it into failure.** The type check, both test gates and E2E are reported as not reached, rather than each producing its own cascade of errors caused by the same broken build.
- **The test gate is now two gates**: `test` runs the hermetic shared and client suites, `test-integration` runs the server suite against a real database. They were always run together; separating them is what lets each sit in the tier its runtime warrants. Both still run on every push.
- **The pipeline's exit code now distinguishes a broken gate from broken code.** `1` still means a gate failed. `2` is new and means a gate could not run at all — a missing prerequisite, a misconfiguration, or a gate that passed without writing the report it promises — because "we do not know" is not the same answer as "no".
- The E2E gate no longer overrides the reporters on the command line; the Playwright configuration now pairs the progress reporter with the JUnit report, and pins the HTML report to never open a browser.
- **`npm test` now names each workspace explicitly**, so deleting or renaming a package's `test` script fails the run instead of silently skipping that package's entire suite.
- **The E2E gate no longer retries a failed spec.** A test that only passes on the second attempt is a defect report about the code or the harness, and retrying it discarded the report.
- **The fast secret scan now reads untracked files too.** It enumerated the git index alone, so a brand-new file that had not been staged yet — most work in progress — was invisible to it. It now reads every tracked and untracked-not-ignored file, the same enumeration the integrity scan uses. Ignored files are still never read, so an untracked `.env` holding real credentials remains the intended way to hold them.
- **Removed eight dependencies nothing used** and declared four that were being used without being declared. `@typescript-eslint/eslint-plugin` and `@typescript-eslint/parser` are supplied by `typescript-eslint`; `postcss`, `autoprefixer` and `@csstools/css-syntax-patches-for-csstree` are not part of a Tailwind v4 build; `@types/bcryptjs`, `@types/node-cron` and `@types/react-window` shadow types those packages now ship themselves. On the other side, `winston` is imported directly by the server, `winston-transport`, `otpauth` and `mongodb-memory-server` by its tests and the E2E harness, and all four were resolving only because another package happened to install them.
- **The database container's health probe now says why it could not start the replica set.** A failure from `rs.initiate` was discarded entirely, leaving an unhealthy container whose probe explained nothing; the expected "already initialised" case now says so, and any other failure is named. Only the error's short code is reported — never replica-set state or a stack trace.
- **A gate can now declare a wall-clock deadline, and one does.** A gate whose subject can HANG — a parser handed an attacker-chosen file — cannot report that through an exit code, because a wedged process produces none. The pipeline's process helper now takes a per-gate deadline, kills a child that outlives it, and reports it as a failure that is distinguishable from an ordinary one. Only the fuzz gate uses it; every other gate is unchanged and unbounded.
- **A test run no longer writes log files into the checkout.** Every logger in the server took the logging library's defaults, which write two rotating files per module relative to the process's working directory — so each run of the server suite appended about 1.6 MB of logs to `packages/server/logs`, ignored by git and therefore by every check, and 448 MB had accumulated across 406 files. No file transports are attached under `NODE_ENV=test` at all; console output is unchanged, in every environment. The test harness's own filesystem guard no longer exempts those directories, so a logger that goes back to the defaults fails the suite immediately instead of quietly filling the checkout again.
- **The static-analysis gate now tells an absent analyser apart from a broken one.** A CodeQL installation that was present but could not run — extracted without execute permission, or unpacked for the wrong platform — failed the gate with a bare exit code and no explanation. It is now probed by running it, the actual cause is reported with the fix, and the gate falls back to Semgrep CE or OpenGrep. It reports itself skipped only when no analyser is available at all, naming each one it looked for.

### Fixed

- **The static-analysis gate had been passing on a weaker engine than the one it named.** The CodeQL bundle unpacked into the local cache was the **Windows** build sitting on a Linux machine, so the launcher went looking for a Java runtime under `tools/linux64` that the archive never contained. The gate detected that it could not run, fell back to OpenGrep exactly as designed, said so in its report — and reported **pass**, because a clean fallback scan is a clean scan. Nothing was wrong with the gate; what was wrong is that nobody read the line where it named the engine, and the twenty reviewed findings in `scripts/ci/codeql-baseline.json` had therefore not been re-checked by anything for as long as the wrong bundle had been in place. With the correct bundle installed, the real suite found three error-severity issues that the fallback's rule corpus does not cover: one genuine catastrophic-backtracking regular expression in the ratchet's baseline-key transform, now repaired at its cause, and two reports against a fuzz fixture that are false — the query does not distinguish a computed `['__proto__']` key, which creates an ordinary own property, from the literal form that sets a prototype, and telling the two apart is the entire subject of that fixture. The two false ones are recorded in the baseline with that reasoning written down in `README.md`; the real one is fixed rather than accepted. The README's description of this gate has been corrected to match what it does — it falls back to Semgrep CE or OpenGrep and names the engine that answered, and reports itself skipped only when no analyser is available at all — and the installation instructions now pin the platform and tell you to probe the binary before trusting it, because a bundle for the wrong platform extracts without complaint and only fails at first use.
- **The static-analysis gate could not fail its own test, and two separate defects were hiding that.** `npm run verify:selftest` plants one defect per gate and requires the gate to go red; for the static-analysis gate it had been reporting the case BLOCKED, because no usable analyser could be found — which reads as "not measured" and is easy to pass over. With the analyser installed, the case ran and reported something worse: the gate **exited 0 with the defect planted**. The first cause was the defect itself, which was not the defect its title claimed — it read a bare function parameter rather than a request value, and the query that should catch it tracks tainted data from an external source to a dangerous sink, so with no source there was nothing to find and the analyser was right to stay silent. The second surfaced only once the first was repaired: the self-test builds a throw-away copy of the tree, the gate resolves the analyser relative to its own location, and the analyser lives in a cache directory that is deliberately never copied — so every run of this case had been quietly proving the FALLBACK engine instead of the gate it names, and that engine's rules do not report the planted injection at a severity this gate fails on. The planted defect is now a real route handler passing a request value into a shell command, verified to trip the gate before being trusted, and the workspace shares the analyser the same way it already shares installed dependencies. The self-test now proves 35 of 36 gates, with the mutation oracle the only one outstanding and recorded above.
- **`SECURITY.md` named a supported version seven releases out of date.** Its table still said `0.1.x` while the project shipped 0.8.0, which is the one line in that document a reader checks before deciding whether their deployment still receives security fixes. It is now pinned to the root `package.json` by a test, like every other place the version appears, so it is a release step that cannot be forgotten rather than one that has to be remembered.
- **Several documented guarantees were stated more strongly than the artifacts support.** `SECURITY.md` and `CONTRIBUTING.md` listed CodeQL as something that runs on every push, when it is optional and the gate substitutes another engine when its CLI is absent. Five places said that the self-test proves _every_ registered gate can fail, without mentioning that a gate whose prerequisite is missing on the machine is reported blocked and counted on its own line rather than folded into the total. The README quoted an end-to-end test count of 195 and `CONTRIBUTING.md` a client branch-coverage figure of 92.45%, both of which had moved. Each of these has been brought back to what the reports actually say.
- **A website address of the maximum length could be saved once and then never edited again.** The 2048-character limit was measured on the address as typed, and the vault adds `https://` to one entered without a scheme — so a bare domain of 2041 to 2048 characters passed the editor, was stored eight characters over the limit, and every later save of that item was refused with "Too big" on the address, with no way to correct it from the item itself. The limit is now measured on the value that actually gets stored, in one place that both the editor and the vault use, and the scheme's length is counted per address rather than assumed: a bare domain grows by eight characters, a protocol-relative one by six, and one that already carries `https://` by none, so an address of the full 2048 characters is still accepted where it always fits.
- **A secret's expiry date in the first century was refused as an invalid calendar date.** The editor advertises a range beginning at 0001-01-01, but the check behind it built its date through an interface that maps a two-digit year into the 1900s, so every date before the year 100 failed. The check now builds the date the way the editor already did, and the accepted range matches the advertised one. Impossible dates — 30 February, a thirteenth month, 29 February in a year that is not a leap year — are still refused, in the first century as anywhere else.
- **Eleven fields on the Bitwarden import path discarded the whole card or identity when one of them was a character too long.** A cardholder name, card number, expiry month or year, security code or brand, and an identity's first name, last name, company, national identification number or passport number all reached validation unbounded, and Bitwarden bounds none of those columns in its own export. A single over-long value therefore failed the item's format check and the entire entry was dropped — every other field of it with it — reported only as one skipped row. All eleven are now trimmed to the limit the vault stores, exactly as the postal-address fields already were, and what was trimmed is preserved in the item's notes. A card's number and security code are the exception: they are trimmed and the trim is reported, but the removed characters are not copied into notes, because notes are shown in the clear beside them.

- **Four test waits that spent real seconds are gone, and two of them were racing.** Three suites paused for just over a second so a freshly minted token would carry a strictly later clock second than the password change before it, and two more slept up to three seconds to step clear of a two-factor code's thirty-second boundary. The waits now advance a frozen clock instead of the wall clock, which is both faster and stricter: sleeping past a boundary made the race unlikely, while stopping the clock removes it — the two-factor step could previously still tick over while the request was in flight, which is the exact failure the wait was meant to avoid. A sixth wait turned out to pin nothing at all: the token it waited for is issued already expired, so the check it guarded holds in every ordering, and it was deleted rather than converted.
- **Multi-select was unreachable for anyone using a screen reader.** Each vault row was itself a button, with the row's selection checkbox inside it — and a button's contents are announced as flat text, so the checkbox was not exposed at all. The checkbox now sits beside the row's activator rather than inside it. Clicking, keyboard activation and the row-sized click target are unchanged.
- **Several controls announced themselves as nothing.** The clipboard-timeout field in Settings, the note-format selector, the match-type selector on each website address and the type selector on each custom field carried no accessible name, so assistive technology could say only "spin button" or "combo box". The notification area had a name that browsers were required to discard, because it was applied to an element that cannot take one.
- **Text that did not meet the minimum contrast ratio.** Secondary labels — a vault row's subtitle and date, card descriptions, the saved-address summary — failed against the surface they sit on while a row is hovered. Everything in the destructive red (Logout, delete actions, inline errors) failed on every surface, as did white text on a destructive button. The online indicator and the email-verified status failed too. All of them now meet WCAG 1.4.3 in the light theme, which slightly darkens the destructive red and the secondary grey throughout, and the two status colours keep their existing dark-theme shades so nothing regresses there. The dark theme as a whole has not been measured, and one known failure remains in it: the destructive red is too dark to read as text on a near-black surface, which needs a separate colour rather than an adjustment to the existing one.
- **The production stack could not start at all when built from a checkout with a restrictive umask.** `COPY` preserves the source file's mode, so on a machine with `umask 077` every file copied from the build context landed in the image readable only by root — including `package.json` and each workspace's manifest. Both images that drop to an unprivileged user then failed at launch: the API exited with `Cannot find package '/app/node_modules/@hvault/shared/index.js'` (Node reads a workspace's manifest to resolve it) and the one-shot index bootstrap exited with a permission error on `/app/package.json`. Because the API waits for that bootstrap to finish, nothing in the stack came up, and the cause was the builder's umask rather than anything in the release. Every file copied from the build context now carries an explicit mode and every copied directory is normalised, so the images are identical no matter where they were built. The container gate builds and scans images without running them, which is why this was invisible; a static check now pins the rule.
- **The one-shot index bootstrap no longer ships a package manager.** It carried npm purely to run one script, and npm's own bundled dependencies were the largest source of vulnerability findings in the whole stack — four advisories across three packages, none of them reachable in a container that runs a fixed command on an isolated network and exits, and none of them fixable, because no npm release replaces those bundled copies. The script is now invoked directly, exactly as the API image already does, which removes the class instead of accepting it again. The accepted-findings list for container scanning is now empty.
- **Submitting a password form before its strength library had loaded started the load a second time.** The registration, password-reset and settings screens each ask for the strength library on mount and again when the form is submitted, and only the finished result was cached — so a submit that arrived while the first load was still in flight re-entered the whole load path rather than joining it. The in-flight load is now shared, and a load that fails can still be retried.
- **Deleting a folder now clears any leftover reference before it answers.** The cleanup that unlinks items still pointing at a just-deleted folder was fired and forgotten, so it could be lost to a restart in exactly the situation it exists to repair — a folder delete that was interrupted partway. It is now completed as part of the request, and a failure in it still cannot fail the delete itself.
- **The Nginx image no longer inherits file permissions from whoever built it.** `COPY` preserves the source file's mode, so on a checkout with a restrictive umask the routing configuration landed in the image unreadable by the unprivileged user Nginx runs as, and the container refused to start with `open() … failed (13: Permission denied)` — a broken deployment whose cause was the builder's umask rather than anything in the release. Both configuration files are now given an explicit read-only mode, so the image is identical no matter where it was built.
- **The container gate can scan images again under rootless Docker.** It looked for the daemon socket at the rootful path, found nothing, and reported a scan failure that read like a broken image.
- **Updated four build-time dependencies carrying denial-of-service and host-confusion advisories** — `brace-expansion`, `fast-uri`, `nanoid` and `undici` — which the image build carried into the bootstrap container. The pin for `brace-expansion` was one patch release short of the fix.
- **Updated `ip-address`, which decides which rate-limit bucket a request counts against.** The version in use carried three advisories covering address misclassification: an IPv4 octet with a leading zero read as decimal where resolvers read it as octal, a CIDR suffix suppressing special-use classification, and IPv4-mapped and NAT64 addresses being misclassified. Each can bypass a trust-boundary check. Nothing else changed.

- **The server test suite could not run on a fresh clone.** One test reached into the bundle-size gate for a filename helper, and that gate reads the built web client the moment it is loaded — so on a checkout that had not built the client yet, the whole suite died at that import with a message about a missing build, and on a checkout that had, every run of the suite silently overwrote the bundle gate's own report and could fail the suite for a chunk being too large. The helper now lives beside the budgets it belongs to, and a check refuses any future test that loads a gate script instead of a library.
- **The deployment drill passed over parts of the stack it had never looked at.** A service added to the stack but not to the drill's expectation table was reported as a warning and nothing more, while every other check in the drill only examines services that table names — so a new container could be started, examined by nothing, and the drill would still report every check passed. It is now a failure, and the table is checked against the stack's own definition on every push.
- **The deployment drill inherited the configuration of the machine it ran on.** It handed the containers a throwaway configuration file, but the stack loads the operator's own file first and the two were combined rather than replaced, so any setting the throwaway file did not mention — mail server, metrics token, documentation endpoint, log directory — reached the containers from the developer's own environment. The throwaway configuration now replaces the operator's rather than extending it, which is what makes the drill a clean room.
- **Coverage of changed lines was not being checked on the branch it matters most on.** The check compared the working tree against the main branch, so a build OF the main branch compared it with itself, found no changed lines, and reported full coverage of nothing — including in the release workflow. On the main branch the subject is now the last commit.
- **The API contract snapshot could be regenerated without anyone noticing.** The compatibility check compares the served contract against a committed copy, and refreshing that copy in the same commit as a breaking change made the comparison agree with itself. The copy is now fingerprinted, so replacing it requires a recorded decision.
- **The artifact smoke test could destroy its own report and waited 45 seconds to notice a refusal to start.** A database that failed to shut down cleanly threw away the record of everything the run had just proved, and a build that refuses to start — the single most likely thing this check catches — exits in about a second but was waited on for the full deadline.

## [0.8.0] - 2026-07-28

### Added

- **"Lock when the tab is hidden" is now a setting you control, and it is off by default.** Hiding the tab used to start a hidden 30-second countdown to lock, no matter what you had set the auto-lock timeout to — switching tabs to look something up was enough to lock the vault. Whether to lock on hiding, and how long to wait first, are now two controls next to the auto-lock timeout. With the setting off, the timeout you configured is the only thing that locks the vault; a hidden tab still locks exactly on schedule, because nothing counts as activity while it is hidden. **If you relied on the old behaviour, turn the setting on and pick a delay.**

### Fixed

- **You can no longer be rate-limited out of your own vault by using it normally.** Signing in, refreshing your session and unlocking the vault all drew on one shared allowance of ten requests per fifteen minutes. Refreshing happens by itself every few minutes for as long as a tab is open, and each unlock spent two more — so a handful of ordinary lock-and-unlock cycles emptied the allowance, and the next sign-in was refused with "too many attempts" on the very first try, with no way in until the window rolled over. Signing in now has its own allowance, which nothing else can spend, and it has been raised from ten to twenty requests per fifteen minutes per address so that several people behind one connection do not exhaust each other.
- **A brief network problem no longer destroys your session.** If the vault could not renew your session — because the server was briefly unreachable, restarting, or rate-limiting — the app treated that as "your session has expired": it signed you out, revoked a session that still had days or weeks left on it, and sent you to the login page with no explanation at all. Only a genuine rejection from the server now ends a session. Anything else keeps you where you are and offers to try again.
- **Unlocking no longer sends you to the login page when something transient goes wrong.** The unlock screen renewed your session on every attempt and treated any failure — including a rate limit or a dropped connection — as a dead session. That was the second half of the loop above: a lock, a failed unlock, a forced sign-out, and a login page that was itself rate-limited. It now renews only when the session actually needs it, tells you what went wrong, and stays put.
- **"Too many attempts" no longer counts against you twice.** Being rate-limited or losing your connection during an unlock used to count as a wrong master password, adding a local cooldown on top of the server's — locking you out twice for one event. Only a genuinely rejected password counts now, and a rate limit tells you how long to wait.
- **A vault that stayed open across a laptop sleeping is now locked on waking.** The idle timer measured how long the app had been running rather than how much time had passed, and a sleeping machine stops that clock: an eight-hour sleep could return with the vault still unlocked and the timer showing minutes left. The deadline is now a point in time, re-checked whenever the window comes back — so returning finds the vault locked, immediately.
- **Scrolling now counts as activity.** Reading a long note by scrolling did not reset the idle timer, so the vault could lock in the middle of reading.
- **Changing your master password on another device no longer looks like typing it wrong.** Unlocking with a session the server had since invalidated reported "incorrect master password", identically and forever, while the cooldown climbed toward ten minutes. It is now recognised and you are asked to sign in again.

### Security

- **Token refresh is now genuinely rate-limited.** Its limit was keyed partly on the refresh cookie, which changes on every successful refresh — so every request was counted as the first request of a brand-new client and the limit was never reached, by anyone. Anyone sending a stream of invalid cookies got the same free pass. It is now keyed on the client address alone, which is the one thing an unauthenticated caller cannot change at will.
- A rejected request that the server refused on its own merits — a locked account, for instance — is no longer automatically sent a second time. Only a genuinely stale cross-site-request token triggers a retry now. The old behaviour doubled the cost of every locked-account sign-in attempt and halved the allowance it drew on.
- The settings, backup-settings and backup-history endpoints, which previously had no rate limit at all, now carry the same per-user limit as the other authenticated endpoints.
- `RATE_LIMIT_WINDOW_MS` and `RATE_LIMIT_MAX` have been removed. They were documented and validated but read by nothing, so an operator who tuned them changed nothing; every limit is per-tier and documented in the README. Leaving them in an existing `.env` is harmless — they are ignored.

## [0.7.0] - 2026-07-28

### Added

- **A card's billing address can now be filled from an address you already saved on an identity.** Most people enter their address once, on an identity, and then retype it for every card. The billing address section now offers "Use a saved address": a searchable list of every identity in your vault that has an address, each row showing the item name, the person it belongs to and the address itself, so you can tell two of them apart before choosing. Picking one fills the six billing fields and opens the section; searching matches on any of those three parts, in any order, so "ada london" finds Ada's London address. An "Undo fill" button appears next to Remove for as long as the fields still hold exactly what was copied, and withdraws itself the moment you edit any of them, so it can never discard a change you made deliberately. Delivery notes are the one part that is never carried over — they belong to a shipping address, not a payment one, and a card cannot store them — and the confirmation says so. Nothing leaves your device: the addresses come from items already decrypted in the browser, and the picker is offered only when at least one identity actually has an address to reuse.
- **An identity's company, Social Security number, passport number and custom fields are now visible and editable.** All four are stored by H-Vault and filled in by the Bitwarden importer, but until now the app rendered none of them and offered no control for any of them, so a retained SSN or passport number could not be viewed, corrected or removed short of deleting the whole item. They now appear on the item (the Social Security and passport numbers masked behind a reveal control, like a card number and CVV) and have controls in the editor, alongside a Notes box for an identity and for a card. Clearing a field removes it from the item rather than storing an empty value, and a vault-list row still never shows any of them.
- **An item that could not be decoded can now be renamed.** Renaming used to be impossible for such an item, because saving the editor would have overwritten its stored contents with the placeholder. A dedicated Rename action changes the name and nothing else — the item's encrypted contents are not part of the request and are left byte-identical — so the notice offers it again alongside move, favourite, delete and restore.
- **Addresses now have a second street line, and an identity's address can carry delivery instructions.** Both a card's billing address and an identity's address gained an optional second street line for an apartment, suite, unit or floor. An identity's address additionally carries free-text delivery notes for a courier ("leave with the concierge", "ring twice"), the kind of instruction a checkout page asks for. Delivery notes are deliberately on the identity only: a card's billing address is a payment attribute, and the shared address shape strips the field, so a card can never hold or display one. Both fields live inside the same encrypted blob as the rest of the item, so the server never sees them, and encrypted backups, restores and vault-key rotation carry them through untouched like every other field.
- The plaintext export carries the second street line in Bitwarden JSON's own `address2` field, so it round-trips exactly. Delivery notes have no Bitwarden field at all and travel as a plain custom field named `Delivery Notes`, which H-Vault reads back into the address on import, so that round-trips too. The format's "what this loses" note states both. Bitwarden CSV and Chrome/Edge CSV omit cards and identities as whole items, as before.

### Changed

- Importing an identity from Bitwarden now maps `address1` to the first street line and folds `address2`/`address3` into the second, instead of joining all three into one line. This is what makes an export-then-import round trip preserve both lines. Note that re-importing a file you had already imported before this release will insert a duplicate for each identity whose `address2` or `address3` was set, because the address it produces is no longer byte-identical to the one stored earlier.
- **Search now looks inside an item's address.** Searching the vault matches nested fields of a decrypted item, so an identity or card is now found by its street line, second street line, city, state, ZIP, country, or delivery notes. None of these had ever been searchable: the search only understood a plain string and a list, and an address is neither. A match still never displays the value it matched on — a row's subtitle comes from a fixed list of non-secret fields — so searching lets you find an item by something you already know, exactly as before.
- An imported address line that is too long to store now reports itself as "Street address truncated" rather than "Street address**s** was truncated"-style copy; the note in the item's notes reads correctly for the plural field names ("Delivery notes", "Street address line 2").
- `npm run type-check` now type-checks the test suites and the Playwright specs as well as the shipped source, via a `tsconfig.test.json` per package and a root `tsconfig.e2e.json`; a new `npm run type-check:e2e` runs the latter on its own. Nothing about the built output changed — this only closes a gap where a test fixture with a wrong or missing field produced no compiler error. Contributors will see the `type-check` gate report errors it previously never looked for.
- Items saved from now on no longer carry a duplicate copy of their name inside their encrypted contents. The name has always been encrypted separately, and the copy inside the contents was discarded whenever an item was read, so nothing ever used it. Existing items are unaffected until the next time they are saved; nothing about how they are read, searched, exported or imported changes.

### Fixed

- Removing a card's billing address no longer strands the keyboard. The Remove button disappears along with the section it removes, and focus was left on nothing — which inside the New Item dialog meant the next Tab jumped to the page behind it rather than staying in the dialog. Focus now follows the section to the "+ Add billing address" link that replaces it.
- Entrance animations are now skipped when the operating system is set to reduce motion. Dialogs, the toast notifications and the saved-address list all animated in regardless of that setting.
- **Editing an item no longer destroys fields the editor does not show.** An identity's company, Social Security number, passport number, notes and custom fields, and a card's notes, are all stored by H-Vault and filled in by the Bitwarden importer, but the item editor rendered no control for any of them. Because saving rewrote the item's entire encrypted contents from just the fields on screen, an edit as small as correcting a typo in the city permanently erased every one of them, with an "Item updated" confirmation and no way to get them back — password history covers login passwords only. Saving now preserves every stored field the form does not itself edit. (All six of those fields have since gained controls of their own, listed under Added above; the preservation stays in place so that the next field added to an item type is safe by default rather than destructive until someone remembers to wire it up.)
- **Editing a secret no longer shifts its expiry by your time zone.** The expiry deadline is a moment in time, but opening a secret and pressing Update without touching the expiry controls rewrote it as a local wall-clock reading with the zone thrown away — moving the countdown by your offset from UTC, silently, every time, and cumulatively when the same item was edited on devices in different zones. Any seconds were dropped as well. The two controls now show the stored deadline in your local time and an untouched expiry is stored back exactly as it was; changing either control stores a new, unambiguous moment, and leaving the time blank means midnight where you are.
- **Editing an identity that has no address no longer causes the next import to duplicate it.** Saving such an identity added an empty address to it, which changed the fingerprint H-Vault uses to recognise an already-imported item — so re-importing the same file afterwards inserted a second copy instead of doing nothing. An address is now stored only when at least one of its fields has content, and clearing every field removes it rather than leaving an empty one behind.
- Saving an item with more custom fields, URLs or recovery codes than the vault accepts no longer produces a Save that silently does nothing. The limit was reported against a field that does not exist on the form, so the message was discarded and no notification was shown either; it now appears as a notification.
- The editor now rejects an invalid regular-expression URL pattern instead of accepting it. A login URL set to "Regex" matching with a pattern that does not compile was accepted by the editor and then refused on save with a general notification; the message now appears against the URL row itself.
- A secret's expiry deadline that falls inside the repeated hour of a daylight-saving change no longer moves an hour earlier when the item is saved without touching the expiry. During that hour two different moments show the same date and time, and one of them was being rewritten as the other.
- Typing a year the vault cannot store into a secret's expiry date (a five- or six-digit year, which some browsers' date pickers accept) no longer deletes the expiry silently on save. It is refused with a message on the date field.
- Length and format limits that the vault enforces on saved contents are now also checked in the editor, so the message appears against the field you are editing instead of in a notification. This covers the username, password, TOTP secret, notes, a secret's description and value, a note's content, the cardholder name and card brand, an identity's names, company, Social Security and passport numbers, and every custom field. A rejection that can only be detected on save is now shown against the offending control too, rather than only as a notification.
- The editor's email and phone checks for an identity now match the ones the vault itself applies. The editor used to accept values the vault rejects — an address with consecutive dots in the local part, a phone number with a `+` that is not leading, or one made only of punctuation with no digit — which were then stored and made the whole identity unreadable on the next open. It also used to reject short phone numbers the vault accepts.
- **An item that could not be decoded can no longer be destroyed by opening the editor.** When an item's contents fail to decode, H-Vault shows a notice instead of the item and keeps the safe actions (rename, move, favourite, delete, restore) working, because none of those rewrite the encrypted contents. The Edit button was offered anyway: opening the editor filled every field from a placeholder rather than from the item, so a single Save overwrote the real contents with an empty item — or, for the other failure mode, re-saved exactly the value that could not be read, leaving the item stuck with no explanation. Edit is now unavailable for such an item and says why.
- The explanation for the unavailable Edit button on an undecodable item is now reachable with a keyboard and announced by a screen reader. The button used to be disabled outright, which takes it out of the tab order, prevents some browsers from showing its tooltip at all, and leaves assistive technology with nothing but "unavailable". It now stays focusable, is announced as unavailable, and points at the notice that explains why; clicking it still does nothing.
- **A save that the vault would not be able to read back is now refused instead of stored.** Item contents are checked against their format before being encrypted, so an over-long or malformed value is reported against the save with a message naming the field, rather than encrypting successfully and only failing on the next read — at which point the unreadable value was the only copy left and the whole item degraded to the "could not be fully decoded" notice.
- An identity's address no longer shows rows of em dashes. Street, city, state, ZIP and country were rendered whether or not they had a value, and because the editor always writes a full address, every identity created in H-Vault displayed an Address panel with up to five blank rows. Each row now appears only when it has content and the panel is omitted entirely for an empty address, matching how a card's billing address has always behaved.
- Multi-line text now displays with its line breaks intact. Notes on a login, card or identity, a secret's description and value, and custom-field values were all shown with their newlines collapsed onto one line, so a multi-line note, a PEM key, or the notes an import writes were hard to read. The stored and copied text was always correct; only the display was wrong.
- A card's billing address section stayed collapsed when opening a card whose street line was empty but whose city, state, ZIP or country was filled in, hiding stored address data behind an "+ Add billing address" link that read as though there were none.
- Address fields in the item editor are now length-checked before saving, with the message shown against the offending field. A value longer than the vault permits was previously accepted and encrypted, then failed validation on the next read, replacing the whole item's contents with the "could not be fully decoded" notice: on a card that meant losing sight of the number and CVV, with no indication of why.
- An imported address line longer than the vault permits no longer discards the entire identity or card at the encryption step. Each line is clamped to its limit and anything trimmed is preserved in the item's notes, matching how over-long URLs and custom fields are already handled. Bitwarden's three address lines are individually unbounded in the source file, and a 21-character postal code was enough to sink an item on its own.

### Security

- `SECURITY.md`'s threat model now covers irreversible loss of your own data through the app itself, which zero knowledge makes a security property rather than a mere reliability one: because the server holds no plaintext, a decrypted item the client overwrites incorrectly cannot be reconstructed from anything. It names the three controls that stand in the way (format validation before encryption, preservation of fields the editor does not render, and read-only handling of an item that cannot be decoded) and states their two limits plainly — that backup restore and vault-key rotation deliberately do not inspect content format, and that none of it replaces keeping encrypted backups.
- Raised the `brace-expansion` version floor to 5.0.8, clearing a high-severity denial-of-service advisory (GHSA-mh99-v99m-4gvg — unbounded expansion length crashing the process out of memory) that affects every earlier version. It reaches the tree only as a build-time transitive dependency and is not reachable from the running server, but it was present in the published container images, which is where the image scan caught it. The floor is pinned in the root `overrides` so it cannot regress.
- The container scan now fails only on findings that are **new**, via `scripts/ci/trivy-baseline.json`, matching how the CodeQL gate has always worked. One finding is accepted under it, stated here rather than buried in the tooling: the same `brace-expansion` advisory also appears inside **npm's own bundled dependency tree** in the one-shot `hvault-bootstrap` image. No `overrides` entry or lockfile of this project can reach that copy, and no npm release yet bundles the fix. The container runs the index script with fixed arguments, takes no untrusted input, publishes no port and exits after a few seconds; the advisory needs attacker-controlled brace patterns. An exception matches only when the CVE, the image, the package **and** the path all agree, so the same advisory in this project's own dependencies still fails the gate, and the entry records what removes it.

### Added

- **A login can now store the 2FA recovery codes for the account it unlocks.** Every login item has an optional list of backup codes, kept inside the same encrypted blob as its password, so the server never sees them. As with every other field, an `overwrite` import replaces a matched item's content wholesale, so recovery codes the imported file does not carry are lost; the confirmation prompt now says so before anything is sent.

- A generic-CSV column whose header mentioned both two-factor authentication and recovery codes, such as `2FA recovery codes`, was automatically mapped to the TOTP Secret field. The codes then landed in the login's TOTP field, where they were truncated at 500 characters and displayed as though they were an authenticator seed. Such a column now maps to the new backup-codes field instead, and a column that merely mentions backups (`Backup email`) is left alone. Every mapping remains overridable in the column-mapping step.

## [0.5.1] - 2026-07-25

### Changed

- The frontend router dependency moved from `react-router-dom` 7 to `react-router` 8. React Router v8 removes the `react-router-dom` package outright and serves the same exports from `react-router`, so this is a package rename: every import was repointed, and no route, redirect, navigation, or URL-parameter behavior changed. Self-hosters who build from source will see `react-router-dom` disappear and `react-router` appear in `packages/client/package.json`; there is no configuration or migration step. Requires Node 22.22+ and React 19.2.7+, both already required by this project.

### Fixed

- **A copied password is no longer erased from the clipboard when you switch tabs or minimise the window.** The clipboard was wiped on every transition to a hidden page, which is exactly the action you take to go and paste, so copying a password and switching to another tab or application frequently produced an empty paste well before the configured clipboard timeout. Whether it happened varied with things that look identical from the outside (whether another window fully covered the browser, and whether the browser had already processed the focus change), which is why it appeared intermittent. Only the configured deadline, a vault lock, a logout, or closing the tab for good now erase a copied secret.
- A clipboard erase that the browser refuses is no longer silently abandoned, leaving the plaintext secret on the clipboard indefinitely. Browsers reject a clipboard write from a window that is not focused, and the erase used to be issued without ever checking whether it succeeded, while the pending deadline had already been cancelled and the secret already marked as cleared. Every later opportunity to clean up (the deadline, a lock, a logout, closing the page) then did nothing. A refused erase is now retried when the window regains focus or becomes visible, when the app is mounted again, and on your next click or keypress in H-Vault. The last of those matters on Firefox and Safari, which require a user gesture for every clipboard write and therefore never accept a purely timer-driven erase at all.
- A refused clipboard erase is no longer stranded by locking the vault. The retry listeners used to live inside the authenticated layout, which is replaced by the unlock screen the moment the vault locks, so an automatic lock in a background tab both refused the erase and removed everything that could retry it, for the rest of the session. They now live above that boundary and also run once on mount, so the erase is retried after unlocking.
- A clipboard write that the browser never answers no longer leaves the secret untracked. The write is abandoned after ten seconds, and because the browser may still complete it afterwards, the secret is treated as though it reached the clipboard so that the deadline, lock and logout all still cover it.
- Locking or logging out while a copy is still being written to the clipboard now erases that value once the write lands, instead of leaving the freshly copied secret behind the lock screen until its own deadline.
- Copying a secret while an earlier secret's erase was due can no longer empty the clipboard you just filled. The erase and the copy could both be in flight at once, and an erase that landed second wrote an empty string over the newly copied value while the app still reported it as present. The two are now mutually exclusive in both directions, and a copy that fails still hands the earlier erase back.
- The 2FA setup secret and the two-factor backup codes copied from Settings are now covered by clipboard hygiene. They previously wrote to the clipboard directly and so were never auto-erased, and were not cleared by locking or logging out either. Copying them also no longer inherits an earlier copy's deadline, which could take them off the clipboard early.
- The "Clipboard will clear in Xs" notice now tracks the real deadline. There is one notice for the whole app instead of one per copy control, it is dismissed when the clipboard is actually erased instead of counting down over an already-empty clipboard, and copying a second item replaces the notice rather than leaving two contradictory countdowns on screen. When the browser has refused the erase it says the clipboard has not been cleared yet and will be cleared on your next action, instead of showing a deadline that has already passed.
- The password generator's Copy button is disabled until the first password has been generated. Clicking it in the brief window before then copied an empty string and reported "Password copied to clipboard".
- The clipboard erase delay is now clamped to the same 5-to-300-second range the settings API enforces, so a malformed or out-of-range value from a profile response can no longer schedule an immediate erase of a secret you just copied.

### Security

- Vault lock and logout now verify that the clipboard erase actually happened rather than assuming it did, and retry it when the browser refused the write. Previously a lock or logout performed while the window was in the background left the copied secret on the OS clipboard with nothing left that would ever remove it.
- Logout now erases the clipboard before contacting the server instead of after, matching lock. On a stalled connection the copied secret used to stay on the clipboard for up to the five-second logout timeout.
- `SECURITY.md` documents the OS clipboard as an explicit part of the threat model: what the erase deadline covers, which engines will and will not let a page erase the clipboard and when, why the erase cannot verify what it is erasing without taking clipboard-read access, and why clipboard state is per tab.
- Resolved GHSA-qwww-vcr4-c8h2 (high severity, CVSS 7.1) by upgrading the router to `react-router` 8.3.0, the first release outside the advisory's vulnerable `>=7.12.0 <8.3.0` range. The flaw is a CSRF bypass that lets an action run before the 400 response in React Router's RSC mode; H-Vault does not use the unstable RSC APIs, so it was not exploitable here, and no H-Vault deployment needed emergency action. It is fixed rather than suppressed because the dependency audit and container image scan both fail closed on it, and because `react-router-dom` had no patched release on any version line — the only remedy is the v8 package. Operators who pin or vendor dependencies should refresh their lockfile.

- New "Leave H-Vault" plaintext-export page at `/settings/export-data`, reached from a distinct entry-point card in Settings. It exports your whole vault to another password manager as an **unencrypted plaintext file** (Bitwarden JSON, Bitwarden CSV, or Chrome/Edge CSV): pick a format, re-enter your master password, confirm an explicit unencrypted-data warning, and download. The file is generated entirely in the browser and never uploaded; the master password is verified by the server before any plaintext is produced; and items that cannot be decoded, or that the chosen format cannot represent, are reported as skipped/omitted rather than silently dropped. It is a deliberately separate surface from the encrypted `.enc` export/backup and shares no control with it.
- New environment variables `REFRESH_TOKEN_DAYS` (default 7), `REFRESH_TOKEN_REMEMBER_DAYS` (default 30) and `TRUSTED_DEVICE_DAYS` (default 30), in whole days, that configure the standard session lifetime, the opt-in "remember me" session lifetime, and how long a device may skip the 2FA step. The defaults reproduce the previous fixed 7-day session behavior exactly. The server refuses to boot unless `REFRESH_TOKEN_REMEMBER_DAYS` ≥ `REFRESH_TOKEN_DAYS` and `TRUSTED_DEVICE_DAYS` ≥ `REFRESH_TOKEN_REMEMBER_DAYS`.
- `POST /api/v1/auth/login` accepts an optional `rememberMe` flag (default `false`). A remembered login extends the session to `REFRESH_TOKEN_REMEMBER_DAYS` (30 days); for a 2FA account it also registers the device as trusted after the 2FA step so it can skip the 2FA prompt on later logins until the trust grant expires (`TRUSTED_DEVICE_DAYS`). The master password is still always required to decrypt the vault. The flag is carried inside the signed 2FA temp token, so it cannot be tampered with at the 2FA step.
- The login screen now has an opt-in "Remember me on this device" checkbox, with a note that it is only for trusted devices and that the master password is still required on every unlock and is never stored. When checked, the choice is honored whether or not the account uses 2FA.
- New `GET /api/v1/user/trusted-devices` endpoint lists the devices allowed to skip the 2FA step (device info and created/last-used/expiry dates; the server-only token hash is never returned), and `DELETE /api/v1/user/trusted-devices/:id` and `DELETE /api/v1/user/trusted-devices` revoke a single trusted device or all of them. A revoked device must complete 2FA again on its next login.
- A remembered session now resumes across a full browser restart: on the next launch the app silently refreshes the session and lands on the Unlock screen (master password only), instead of the login screen. The vault key is still re-derived from the master password on unlock and is never persisted. The remembered session is abandoned only when the server confirms it is gone; a transient offline or server-restart failure keeps it for the next launch.
- The Sessions page (Settings → Active Sessions) now has a "Trusted devices" section listing every device allowed to skip the two-factor step, with its browser/OS, IP and trusted/last-used/expiry dates, a per-device revoke, and a confirmed "Revoke all". The copy explains that revoking a device forces it to complete two-factor authentication again on its next sign-in.

### Changed

- The `MAX_SESSIONS` limit (50) is now enforced as a real per-device cap: signing in on a new device evicts your oldest active session once you exceed the limit, instead of the limit only bounding the sessions list. Only live sessions are counted and evicted — the short-lived internal rotation records that back stolen-token detection are never touched — so this never logs another device out spuriously and never weakens reuse detection. The Sessions list now shows only live sessions, so its count matches the enforced cap.
- The in-memory breach-range (HIBP) cache is now bounded by a measured byte budget (`HIBP_CACHE_MAX_BYTES`) as well as by entry count, keeping worker memory within its budget even when cached ranges are unusually large. The PM2 `max_memory_restart` ceiling was raised to 768 MiB to fit one worker holding a full cache plus its ordinary heap (the ceiling is per worker, not aggregate across workers).
- The breach-corpus seeder is now part of the compiled server output, so it can run inside the production Docker image (which ships no `npm` and no `tsx`) with `docker compose exec hvault-app node packages/server/dist/cli/seedBreaches.js`. Local usage is unchanged: `npm run seed-breaches -w packages/server` still works and takes the same flags.

### Removed

- Removed the `JWT_REFRESH_EXPIRY` environment variable. It was validated and documented but read by no code path — the refresh-token lifetime was always the hardcoded 7 days regardless of what it was set to — so an operator who set, say, `JWT_REFRESH_EXPIRY=30d` silently still got 7 days. Configure the session lifetime with the new `REFRESH_TOKEN_DAYS` instead.

### Fixed

- The client production build no longer fails intermittently on Windows from an upstream Rolldown native teardown crash (exit code `0xC0000005`) that fires after the bundle and service worker are already written. `npm run build` now retries `vite build` exactly once, and only on that specific native-crash exit code; ordinary build errors still fail immediately, so a green build always means a genuinely complete one.
- The empty-cache boot log and the operations docs no longer tell operators to run `npm run seed-breaches` from inside the production app container, where `npm` does not exist; they now point at the compiled `node packages/server/dist/cli/seedBreaches.js` command that actually runs there.
- The local CI pipeline (`npm run ci`) no longer emits a Node `DEP0190` deprecation warning on Windows. Its npm-gate runner now pre-joins arguments into the shell command string — byte-for-byte the command line Node builds internally — instead of passing an args array alongside `shell: true`; the executed command is unchanged.

### Security

- Trusted devices for the "remember me" 2FA-skip are stored as a server-side record, never a client-asserted flag: the browser holds only a random opaque token and the server stores just its SHA-256, so trust cannot be forged and can be revoked centrally. The raw token appears only in the `Set-Cookie` header (scoped to `/api/v1/auth`) — never in a response body, a log, or the database — and the grant is capped per account (`MAX_TRUSTED_DEVICES` = 10, oldest evicted first) with a hard TTL at its absolute expiry. Three audit actions were added — `trusted_device_grant`, `trusted_device_revoke`, and `trusted_device_rejected` — bringing the audit log to 41 distinct operations.
- The trusted-device 2FA skip is consumed only after the password is verified. `POST /api/v1/auth/login` checks the `trustedDevice` cookie strictly after the bcrypt comparison and lockout evaluation, and only when the cookie is actually present, so a wrong password never reaches the check and an ordinary 2FA login (no cookie) does no lookup, clears no cookie, and writes no audit. On a match the token is consumed and rotated (a fresh token replaces it, carrying the original expiry forward so the trust window is never extended), and the session honors the request's own `rememberMe` (an unchecked box yields a standard-length session, never a silent 30-day one). Any anomaly — an unknown, expired, replayed, or another user's cookie — fails closed to the normal 2FA prompt, clearing the stale cookie and auditing `trusted_device_rejected`, and never revokes the account's other trusted devices.
- A trusted device's 2FA-skip is now dropped automatically on every event that changes the account's authentication footing, so trust can never outlive the second factor it was granted against: a password reset or change, enabling or disabling 2FA, regenerating backup codes, "log out everywhere", stolen-refresh-token reuse detection, and account deletion all revoke the account's trusted devices. Detecting a replayed (stolen) refresh token revokes the trusted devices along with the token family, so an attacker who steals a cookie cannot then skip 2FA. Ordinary single-session logout deliberately does not revoke trust — that would defeat the feature — and the revocation is centralized in one shared helper so no path can silently skip it.
- The trusted-device and session revocation endpoints (`DELETE /api/v1/user/trusted-devices`, `DELETE /api/v1/user/trusted-devices/:id`, `DELETE /api/v1/user/sessions/:id`) now carry the per-user request limiter their listing sibling already had, so an authenticated — or session-hijacked — caller cannot flood the audit log or churn revocation by hammering them.
- The portable plaintext export is confined to its own page and code path, physically separate from the encrypted `.enc` export/backup, so a user can never confuse "back up my vault" with "hand out every password in the clear"; the separation is itself a safety control. The exported file is unencrypted plaintext — every password, TOTP secret, card number and note — generated only in the browser, gated behind master-password re-verification and an explicit confirmation dialog, and never written to any store, `localStorage`, `sessionStorage`, or the console. CSV values are quoted per RFC 4180 but deliberately never altered (no formula-injection mutation, which would corrupt legitimate passwords and does not reliably stop spreadsheet formula execution anyway); the page instead warns not to open the file in a spreadsheet and to delete it after importing elsewhere.

### Added

- New `POST /api/v1/tools/check-password-breach/batch` endpoint that checks many password hash prefixes in one request (k-anonymity preserved: only the first 5 hex chars of each SHA-1 hash ever leave the device). A breach scan of a large vault now costs a handful of requests instead of one per password. A dedicated rate-limit tier (`breachBatchLimiter`, 300 / user / 15 min) sizes it to cover a full-vault scan without ever returning a partial result.

- Vault Health breach findings and weak-password scores now persist on the device, encrypted with your vault key, so they survive a page refresh, an auto-lock, and a browser close — you no longer have to re-run the long breach scan and wait on the page each time you return. A "Last checked" label shows how old the saved results are, "Check for Breaches" runs a fresh scan and replaces the saved results only after it fully succeeds (a failed or interrupted scan keeps the previous results), and the saved snapshot is cleared on logout.
- A persistent, cross-account server-side cache of breach-range lookups (MongoDB): once any account has checked a given hash prefix, subsequent checks by any account are served locally until the entry ages out, so repeat scans no longer re-query the third party and survive server restarts. If the upstream service is unreachable, a cached range is served as a fallback and a prefix is never reported as "not breached" on failure.
- New opt-in command `npm run seed-breaches -w packages/server` imports the full Have I Been Pwned Pwned Passwords corpus into the local cache for fully-offline / zero-third-party-dependency breach checking. It is idempotent and resumable; an optional scheduled refresh is available via `BREACH_SEED_REFRESH_CRON` and `BREACH_SEED_AUTO`.
- New environment variables `BREACH_CACHE_TTL_DAYS` (default 30), `BREACH_SEED_AUTO` (default `false`), and `BREACH_SEED_REFRESH_CRON` (unset) to tune the breach-range cache and the optional seed refresh.

- Vault Health scores password strength in a background Web Worker and windows long result lists, so the page stays responsive on large vaults instead of freezing the browser. The breach check also deduplicates passwords first, so identical/reused passwords cost a single lookup.
- Breach-range requests to Have I Been Pwned now send the `Add-Padding` header and discard the count-0 padding rows, so the queried prefix cannot be inferred from the response size by an on-path observer.
- **The local development server now runs on port 5173 (Vite's default) instead of 3000.** On Windows, Hyper-V/WSL2/Docker reserve dynamic TCP ranges that routinely include 3000; a reserved port fails to bind with `EACCES` rather than `EADDRINUSE`, which aborted `npm run dev` outright and made the whole Playwright E2E suite fail with an unexplained "Timed out waiting from config.webServer". The port is resolved by a single helper (`resolveDevPort`) that both the Vite config and the Playwright config read, so they can never drift, and it is overridable through the process environment with `VITE_PORT` (for example `VITE_PORT=5180 npm run dev`). The dev Docker stack now publishes `127.0.0.1:5173` and the default `CORS_ORIGIN` is `http://localhost:5173`. Production is unaffected: the built SPA is served by Nginx behind the single published port, not by Vite.
- The "Vault" sidebar item is highlighted on the vault list and on an individual item page, but no longer lights up at the same time as "Vault Health" when you open the Vault Health page.
- Pin the production Docker image base to `node:24-alpine3.23` instead of the floating `node:24-alpine` tag. The floating tag had rolled onto Alpine 3.24, whose musl userspace crashes `npm` at process launch (SIGSEGV, exit 139) under the WSL2 kernel used for local image builds, so `npm ci` failed and the images could not be built there. The pinned variant carries the identical Node 24.18.0 runtime and builds cleanly; there is no change to the running application.

### Fixed

- The Vault Health page no longer freezes or hangs the browser on vaults with many passwords; password-strength analysis was moved off the main thread.
- The OpenAPI document now describes the `POST /api/v1/tools/check-password-breach` response as the range text the endpoint actually returns, instead of a `{ found, count }` object it has never returned. A client generated from the spec no longer reads fields that are not there.
- The sidebar no longer highlights both "Vault" and "Vault Health" at once when viewing the `/vault/health` route.

### Security

- The breach check now surfaces passwords it could not verify (for example a failed or rate-limited lookup) instead of reporting them as "not breached", so an unchecked password can no longer be mistaken for a safe one. Restored results are held to the same rule: a password the saved snapshot never covered — one added or edited since the last scan, such as every entry of a large import — is counted as unverified and keeps the "could not be checked" warning on screen, rather than being quietly omitted and leaving a green "No breached passwords found" over credentials nothing has looked at.
- If password-strength analysis cannot complete (for example the analyzer fails to load), Vault Health now shows an explicit "could not analyze" warning instead of a misleading "No issues found", so a failed analysis is never mistaken for a clean result.
- Added an explicit `worker-src 'self'` Content-Security-Policy directive for the new password-strength Web Worker (same-origin only; never a `blob:` worker).
- The persistent breach-range cache stores only PUBLIC Have I Been Pwned data keyed by the 5-char SHA-1 prefix, with no per-user linkage and no stored suffix match, so it preserves the zero-knowledge model (the server still only ever receives the prefix, never a password or full hash). The on-device saved Vault Health results are encrypted with the vault key and remain encrypted at rest across a lock, exactly like the wrapped vault key.
- Force `shell-quote` to `>=1.9.0` through a dependency override, resolving CVE-2026-13311 (HIGH: denial of service via inefficient input parsing). It was pulled in transitively at `1.8.4` by the `concurrently` dev dependency and surfaced in the `bootstrap` image once the image build was unblocked.

## [0.3.0] - 2026-07-22

### Added

- `POST /api/v1/tools/import` accepts a structured `operations` payload — explicit `inserts` and `updates`, where each update names the id of the existing item it replaces — and answers with `{ insertedCount, updatedCount }`. Two new rejections come with it: `400` when an update names an item that does not exist, is in the trash, or belongs to someone else (it is never silently skipped), and `409` when another import for the same account is already running, when a vault-key rotation is in flight, or when an item an update targeted was changed or removed while the request was being applied. With `skip` or `overwrite`, re-running the import is safe: it re-resolves against the current vault and performs only what is left. With `keep both` — which by definition never matches anything — a re-run adds the rows that already landed a second time, and the client now says so instead of advising a retry.
- Importing with `overwrite` now asks for confirmation before anything is sent. The prompt states how many existing items will be modified and how many passwords will change, and warns that a matched item's name and content are replaced by the imported version — so anything the file does not carry (a TOTP secret, notes, custom fields) is lost, with only the password recoverable from history.
- Each vault list row now carries a second, distinguishing label beside its type badge: a login's username (or, when it has none, the site it belongs to), a card's last four digits behind a mask, or an identity's name (or email). Notes and secrets have none, and no password, CVV, SSN, TOTP seed or secret value is ever shown — so several accounts on one site are finally told apart at a glance. The full value is available as a hover tooltip, so a subtitle the row is too narrow to show is still readable.
- An import now reports what happened to every row: how many were imported, updated, already up to date, skipped as duplicates of existing items, dropped as duplicates within the file, and skipped as unusable — with the reason for each unusable row. The counts add up to the number of rows the file contained.

### Changed

- **Breaking:** the `POST /api/v1/tools/import` request contract is now `operations` only. The previous `data` envelope (a JSON string of encrypted items that the server de-duplicated by name) has been removed, and a request carrying it is rejected. A request is bounded by 10,000 combined operations rather than by that envelope's 1 MB string limit; the byte ceiling is now the server's ordinary 2 MB request-body limit, and the client keeps splitting a large migration well inside it.
- An import row the server cannot use — one missing an encrypted field, or carrying a malformed search hash, tag or password-history entry — now rejects the whole request with `400` and writes nothing, instead of being silently filtered out while the rest of the file imported. Nothing is dropped without being reported.
- **Import now identifies items by their decrypted content, not by their name.** A login matches on its site and username, and every other item type on its exact content; the match is computed in the browser, where the plaintext lives, and is never sent or stored. Ten accounts on one site therefore stay ten items instead of collapsing into one, re-importing the same file changes nothing, and how a large import is split into requests can no longer affect the result. `skip` (the default) still never modifies anything, and `keep both` still never matches.
- **`overwrite` can now modify an existing item in place** — replacing its content and its name with the imported version — where before, name-matching made that unpredictable. It requires the confirmation described above, and the password it replaces is always kept in that item's password history.
- Re-importing a native H-Vault export now restores an item's password history along with it, instead of recreating the item with an empty history.
- An imported login whose source had no title is now named `<site> (<username>)` instead of just `<site>`, so several accounts on one site no longer arrive as identical-looking rows. Only a name derived from the URL is affected — a title the source supplied is never changed — and matching is unaffected for any login with a usable site and username, because such a login is matched on those rather than on its name.
- Vault list sorting is now a total order: rows that tie on the chosen key are settled by name, then by the new row subtitle, then by an internal identifier. Ten same-named logins used to appear in whatever order they were loaded in — which differed between a fresh fetch and an offline read — so sorting by Name did nothing for exactly the case a bulk import creates. Reversing the sort direction now produces the exact reverse of the ascending order.
- The server no longer decides what is a duplicate. It validates ownership, field lengths and the per-account item limit, then applies exactly the operations it was given; `conflictStrategy` is recorded for the audit log but no longer acted on, because matching now happens in the browser where the decrypted content lives. An import update rewrites item content only — it can never change an item's tags, favorite flag, folder or type.
- Concurrent imports for one account are now serialized, so two overlapping imports can no longer both pass the per-account item limit and push the vault over it. Where the database supports transactions, an import's writes also commit or roll back as a unit, and the limit is re-checked against the state those writes actually see.

### Fixed

- Import no longer treats two unrelated logins as the same item when one of their web addresses is a match **pattern** or contains a stray backslash. A URL that says `accounts\.google\.com` was being read as the site `accounts`, so a Google and an Okta login sharing a username collapsed onto one identity — with `overwrite` replacing one with the other, and `skip` reporting a genuinely new credential as a duplicate and never importing it. A pattern now identifies no site, matching falls back to exact content, and the same rule applies to any address whose host the URL parser silently rewrites. The vault list stops labelling such a row with that misread host, too.
- The OpenAPI document now describes the import request as tightly as the server validates it: a tag has a minimum length, an item id and a folder id carry their expected format, the operation lists have their default, and the success response documents the `message` it has always returned. A client generated from the spec no longer sends bodies the spec called valid and the server rejects.
- Corrected two statements in the documentation that promised more than the code delivers: a rejected import writes nothing on every failure **except** one — if an item an update targeted is changed or removed mid-request, a MongoDB deployment without a replica set (the default) may already have committed earlier operations from that same request. Re-running remains safe. Relatedly, a deployment whose connection string names a replica set that is not actually configured does not "silently fall back" to non-transactional writes as its startup warning claimed; the affected endpoints fail outright, writing nothing.
- The OpenAPI document no longer advertises `422` for a request that fails schema validation. Every endpoint validates through the same middleware, which has always answered `400`, so a client generated from the spec handled a status the API never sends and missed the one it does.
- An import now refuses to run rather than resolving against a vault it could not fully load — a failed or superseded item fetch, a lock part-way through, or a read served from the offline cache. Matching against a partially loaded vault would have made every existing item look new and duplicated the entire file.
- Vault list rows are no longer packed too tightly once the list passes 50 items. The virtualized list was told each row was 72px tall when it actually renders at 78px, leaving a 2px gap between rows instead of the 8px the shorter list uses.
- Bitwarden import no longer silently drops parts of an item. An identity's `title`, `middleName`, `username` and `licenseNumber` — none of which the vault has a dedicated field for — are now preserved in the item's notes under clear labels instead of being discarded. Bitwarden SSH-key items (previously imported as an empty note that lost the key entirely) are now imported as a login whose private key, public key and fingerprint are kept in clearly-labelled custom fields, with the private key masked. A Firefox export's `httpRealm` column (which identifies an HTTP Basic/Digest auth entry) is now preserved in notes; the remaining Firefox metadata columns (`formActionOrigin`, `guid`, and the `time*` timestamps) are intentionally not imported, as they have no vault field and would clutter every row.
- Importing an entry with an over-long field no longer discards the whole item. A username, password, note, URL, or custom-field value that exceeds the vault's per-field limit is now clamped to that limit instead of failing validation and dropping the entire entry (password included). The truncated overflow — and the full original URL or username — is preserved in the item's notes under a clear label; a password is clamped but, for safety, is never copied into notes. Custom fields beyond the 100-per-item limit are summarized in notes rather than lost. A scheme-less URL is clamped with room for the `https://` the vault adds, so a very long bare domain no longer becomes a permanently unreadable item.
- `package-lock.json` now records the current project version. It was left at `0.1.2` when 0.2.0 was cut, so the first `npm install` on a fresh clone rewrote the lockfile unprompted. No dependency, resolution or integrity hash changed.

### Security

- Import duplicate detection moved off the server entirely: the match key is computed in the browser from decrypted content and is never transmitted or stored, so the server no longer receives the name-equality signal it used to act on. One consequence is stated plainly rather than glossed over — under `overwrite`, the server does see which of your own items an import updates, an equivalence between imported entries and stored items it could not previously compute. It never leaves your own vault and exposes no plaintext; `skip` (the default) and `keep both` send no updates at all. `SECURITY.md` documents this.

## [0.2.0] - 2026-07-21

### Added

- Real client-side import for external sources: Bitwarden (JSON and CSV), LastPass, KeePass, Chrome/Edge, Firefox, 1Password, and a generic column-mapping CSV. The browser parses the export, converts each entry to a vault item, and encrypts it with the vault key before upload — no credential, note or field value leaves the device in the clear. Source folders/groups are preserved as tags, and tags are stored in plaintext (they are indexed server-side), so an import makes your source folder names visible to the server; see `SECURITY.md`. A source without a title (e.g. Firefox) derives the item name from the URL host.
- `chrome`, `firefox`, and `onepassword` added to the `/tools/import` `format` values; unsafe-scheme URLs (e.g. `android:`) are dropped from a login's URI list and preserved in its notes.
- `MAX_IMPORT_FILE_SIZE_BYTES` (8 MiB) client-side import-file ceiling; large imports are now split into several size-bounded requests automatically, with per-batch progress shown on the Import button.

### Changed

- Import parsing and encryption are now entirely client-side. The `/tools/import` endpoint accepts only already-encrypted native items (`{ items: [...] }`) regardless of `format`, which is retained purely as audit metadata; the request no longer accepts `csvMapping`.
- Duplicate detection during import matches an incoming item against items already stored, never against other items in the same request — unchanged — but a large import is now split into several sequential requests, so items sharing a name across a batch boundary are treated as duplicates of each other. Two entries both named "Amazon" land as two items when they fall in the same batch, and as one (under `skip`) when they straddle two. Imports small enough to fit one request are unaffected. If you need every same-named entry kept, use the `keep both` conflict strategy.
- `/tools/import` now has its own rate limit (60 requests per user per 15 minutes) instead of sharing the 10-per-IP heavy-operation budget with export, backup and bulk operations. A large migration is uploaded as several encrypted batches, which could otherwise exhaust that shared budget part-way through and stall the import.

### Fixed

- Importing an external export (e.g. a Firefox-exported `.csv`) no longer fails with "No valid items found to import (all items had missing encryption fields)". External formats were never parsed or encrypted on the client, so the zero-knowledge server rejected every row; they are now parsed and encrypted in the browser first.
- Re-importing a large native H-Vault export no longer fails on the 1 MB per-request cap: the encrypted payload is sent in batches.
- The CSV mapping preview now uses an RFC-4180 parser that correctly handles quoted fields containing embedded newlines (the previous line-split parser split them into broken rows).
- A Bitwarden identity carrying an unusual email or phone number (for example a number with an extension, or `+1 555 CALL-NOW`) is no longer discarded wholesale. Those two fields are validated against the same rules the vault enforces and moved into the item's notes when they don't fit, so the rest of the identity — name, address, passport, SSN — is preserved.

### Security

- Removed the server-side plaintext-CSV import branch. It mapped raw CSV cells straight into fields named `encrypted*`, so a mis-triggered client could have stored plaintext secrets server-side, defeating the zero-knowledge guarantee. The server now never parses plaintext on the import path.

## [0.1.2] - 2026-07-20

### Added

- `MONGO_APP_USERNAME` and `MONGO_APP_PASSWORD` environment variables for the least-privilege database account. `MONGO_APP_PASSWORD` is required and ships empty, so the stack refuses to start until it is set — existing deployments must add it to `.env` before the next `docker compose up`.

### Changed

- Moved the default Docker network blocks from `172.28.0.0/24` / `172.28.1.0/24` to `172.31.240.0/24` / `172.31.241.0/24`. Docker allocates its own bridges from the bottom of `172.17.0.0/12` and hand-pinned stacks tend to claim the low `172.2x` blocks, so the previous defaults collided with an existing stack and `docker compose up` failed outright with "Pool overlaps with other one on this address space". Both blocks remain overridable via `HVAULT_EDGE_SUBNET` / `HVAULT_DATA_SUBNET`.
- Documented that `docker compose up -d --wait` can report `container hvault-nginx is unhealthy` while the stack is serving normally, which happens only when re-running it to recover from an app outage longer than about 75 seconds. Nginx's probe runs through the proxy, so it is marked unhealthy during the outage and Compose treats that as terminal rather than waiting for the next probe. The deep probe is deliberate and is retained: it is what proves the whole single-port path at deploy time.

### Fixed

- `GET /api/v1/health`, `GET /api/v1/config` and `GET /api/v1/metrics` now answer correctly while MongoDB is unreachable. Their rate limiters were backed by MongoDB, so a database outage made each request stall for the driver's full server-selection timeout and then fail closed — replacing the intended `503` with `database: "disconnected"` with a generic 500 that both container health probes timed out on before it was even written. Those two limiters now count in process memory, so the endpoints no longer depend on the database they exist to report on. The ten limiters guarding database-dependent routes are unchanged and still fail closed.
- Pinned the internal Nginx to two worker processes instead of `worker_processes auto`. `auto` counts the **host's** CPUs and ignores the container's quota, so the web service forked one worker per host core inside its `cpus: '0.5'` / `mem_limit: 256m` / `pids_limit: 100` budget — measured as four workers on a four-core host, and unbounded on larger machines.

### Security

- The application and index-bootstrap containers now authenticate to MongoDB as a user restricted to `readWrite` on the `hvault` database, instead of as the cluster root user. A new one-shot `hvault-db-init` service provisions that account before the rest of the stack starts, and the app/bootstrap `environment:` blocks blank the discrete `MONGO_ROOT_*` / `MONGO_APP_*` keys that `env_file` would otherwise inject, so the root credential reaches only the database itself and that one short-lived container. A compromise of the application no longer confers administrative access to the cluster, other databases, or user management.

## [0.1.1] - 2026-07-20

### Changed

- Upgraded server, client and tooling dependencies to their latest compatible releases, including `@hiprax/logger` 1.1, `helmet` 8.3, `express-rate-limit` 8.6, `mongodb` 7.5, `react-hook-form` 7.82, `lucide-react` 1.25, `vite` 8.1.5, `tailwindcss` / `@tailwindcss/vite` 4.3.3, `postcss` 8.5.20, `autoprefixer` 10.5.4, `eslint` 10.7, `typescript-eslint` 8.64, `prettier` 3.9.5, `tsx` 4.23.1 and `lint-staged` 17.1. TypeScript is deliberately held at the 6.x line and `@types/node` at the 24.x line to stay aligned with the supported type-check toolchain and the Node 24 runtime.
- Fatal-crash handling (uncaught exceptions and unhandled rejections) is now captured through the logger's process-wide coordinator, which records a single crash entry with a full stack trace plus process and OS context and flushes the log transports under a bounded timeout before the process exits with a non-zero code.

## [0.1.0] - 2026-07-14

First public release.

### Added

**Vault**

- Zero-knowledge vault for five item types — logins, secrets, notes, cards and identities — with full CRUD, search, folders, tags and favorites. All data is encrypted client-side with AES-256-GCM before it reaches the server; the master password never leaves the device.
- PBKDF2-SHA256 (600,000 iterations) key derivation splitting into a Master Encryption Key that never leaves the client and an auth hash that does.
- Client-side vault key rotation with a server-side write fence, idempotent retries, and a transactional path on replica sets.
- Nested folders with circular-reference detection, depth limits and drag-to-reorder.
- Soft delete with a 30-day trash auto-purge, plus restore and permanent delete.
- Password history (up to 10 previous passwords per login item, individually encrypted).
- Built-in TOTP authenticator for stored login items.

**Tools**

- Password generator with a character-set mode and a passphrase mode (2048-word EFF-based list, exactly 11 bits of entropy per word). Strength is reported as exact information-theoretic entropy against a NIST-calibrated five-band scale, with an honest average-case offline-GPU crack-time estimate.
- Vault health checks: weak, reused, old and breached passwords, and logins with no TOTP configured.
- Breach detection via HaveIBeenPwned k-anonymity (only a 5-character SHA-1 prefix leaves the server).
- Standalone client-side File Encryption tool: encrypt any file with a password to a self-contained `.enc` container (Argon2id envelope encryption, sealed filename/mime metadata, embedded integrity hash). Account-agnostic — the file never touches account keys and never leaves the browser.
- Import from Bitwarden, LastPass, KeePass, CSV and JSON with skip / overwrite / keep-both conflict strategies; encrypted JSON export gated behind password re-authentication.

**Security**

- Two-factor authentication (TOTP) with bcrypt-hashed backup codes, regeneration, replay protection and brute-force throttling at the 2FA step.
- Refresh token rotation with reuse detection and family revocation; access tokens invalidated immediately on password change.
- Account lockout after 10 failed attempts with progressive delays and an unlock email, applied so that it never becomes an account-enumeration oracle.
- CSRF protection via an HMAC-SHA256 double-submit token with constant-time verification.
- MongoDB-backed rate limiting across twelve tiers, keyed per IP, per email, per user or per session, with IPv6 `/64` subnet aggregation.
- Encrypted email backups with a separate backup password (zero-knowledge), HMAC-SHA256 integrity signatures, and repeat-safe restore that re-encrypts rows to the account's current key rather than adopting the backup's.
- Searchable audit log covering 37 operations, with TTL-based retention.
- GDPR account deletion that atomically cascades across every collection.

**Platform**

- Self-contained Docker Compose stack — internal Nginx, Express API, one-shot index bootstrap, and MongoDB as a single-node replica set — publishing exactly one loopback-bound host port for the host's system Nginx to terminate TLS in front of.
- PM2 clustering as an alternative deployment path, with distributed MongoDB job locks so background jobs never double-run.
- Progressive Web App with offline read access via IndexedDB, dark/light/system themes, keyboard shortcuts, virtualized lists and WAI-ARIA-conformant components.
- Local CI pipeline (`npm run ci`) running eleven gates — including container builds with Trivy scanning and CodeQL — from the `pre-push` hook.
